# PDF 转 Word

把 PDF 讲义转成 Word，**文字、公式、表格、图片都是原生对象**，不是截图。
公式转出来是 Word 原生公式，可以直接编辑、可以被搜索。

金石工作台（`edu_book_generator`）的专精版——那边做「PDF → 题库 → 重新组卷」，
这边只做「PDF → Word」这一段。

**最新发行版**：[v0.0.1](https://github.com/kiryusento2017/pdf_to_word/releases/tag/v0.0.1)

---

## 给使用者

下载 `PDF2Word-Setup-v0.0.1.exe`（357 MB），双击 → 选文件夹 → 解压完成 →
双击里面的 `启动.cmd`。装完占硬盘约 1.7 GB。

**三件事得先知道**：

1. **必须装微软 Office**。公式要用 Office 自带的 `MML2OMML.XSL` 转换，
   那是微软的文件不能随本软件分发。**只装 WPS 不行**——实测扫过 WPS 的
   3506 个文件，一个 `.xsl` 都没有。软件打开时会自己检查并告诉你。
2. **别装在 `C:\Program Files`**，路径里也别有中文和空格。
   所有文件都留在软件自己的文件夹里，而那个位置普通用户写不了文件。
3. **第一次打开要下识别模型**（约 4.6 GB）。软件会并发实测各下载源的
   真实速度，最快的默认选中，直接点开始就行。

不想用了直接删掉整个文件夹，不留注册表、不留 AppData。转好的 Word 不受影响。

更新：软件里点「检查更新」→ 自动下载安装（0.4 MB）→ 点「立即重启」。
不用再来 GitHub。

## 界面

620×440 的小窗口，一屏干完：

```
┌ 添加文件  添加文件夹  移除全部        输出：跟原 PDF 放一起  更改 ┐ 工具条
├──────────────────────────────────────────────────────────────┤
│ ☑ 解不等式.pdf                                        10 页  │
│ ☑ 电场中力的性质.pdf          第 7、12 页没有文字层    23 页  │ 主体
│ ☑ 圆锥曲线综合.pdf                                     8 页  │ 永远是
│ ● 加密的文件.pdf              这个 PDF 加了密码，打不开       │ 这张表
├──────────────────────────────────────────────────────────────┤
│ ● 显卡 ✓ · Office ✓  检查更新     选中 9 份 · 128 页 [开始转换]│ 状态栏
└──────────────────────────────────────────────────────────────┘
```

**转换时这张表原地变，不跳屏**：顶部换成「还要约 14 分 23 秒」加总进度条，
每行显示自己的状态（绿点完成、蓝点正在转、灰点排队），转完的行就地长出
「打开 / 文件夹」两个链接。

环境自检压在状态栏，只有必须让用户拿主意时才拦主区：转换引擎缺失（拦死）、
没装 Office（引导去装）、安装目录不可写（告诉他挪地方）。显卡不满足时给
「仍然继续」和「退出」两个按钮**自己选**，并写明具体要等多少分钟。

## 转出来是什么样

同一份讲义（10 页数学）实测：

```
公式 213 个   全部是 Word 原生公式对象，可编辑可搜索，不是图片
表格 2 个     含合并单元格，有边框
图 4 张       按原书尺寸还原（4.45 / 1.29 / 1.61 / 1.25 英寸）
用时 262 秒   其中 MinerU 提取占绝大部分
```

## 进度条为什么显示「还要多久」而不是百分比

因为百分比在这里是误导。MinerU 的阶段进度是真的（直接解析它的 tqdm 输出），
但各阶段耗时差 100 倍——同一次转换的真实时间线：

```
分析版面  0→10     16 秒
识别中    0→10    122 秒   ← 占 42%
识别中    0→202   244 秒   ← 占 49%
定位文字  0→188   249 秒
处理页面  0→10    250 秒   ← 只要 1 秒
```

「分析版面 10/10 完成」看着像快好了，其实才走了 6%。所以首屏显示剩余时间：
页数在体检时就知道，速率是实测的（GPU 26 秒/页、CPU 46 秒/页），
转完一份后还会用真实耗时反推速率替掉出厂估值。

估不出来时显示「正在估算…」——宁可不显示，也不给一个编的数。

## 公式：必须走 Office 的 XSL

```
LaTeX --KaTeX(打包的 node)--> MathML --MML2OMML.XSL(用户的 Office)--> OMML
```

**2026-09-01 起 XSL 是硬性要求，不降级到 Pandoc。** 之前的策略是
「有 XSL 用 XSL，没有退 Pandoc」，改掉是因为两条路的产物有**实质差异**，
不是风格差异：

| | Office XSL | Pandoc |
|---|---|---|
| 空集 ∅ | `∅` U+2205 | **`⌀` U+2300 直径符号，是错的** |
| `\leqslant` | `⩽` U+2A7D | `≤` U+2264 |
| 括号 | OMML 定界符，Word 里随内容伸缩 | 当成普通文字 |

与其让一部分人拿到次等产物还不知情，不如在门口说清楚要装 Office。
公式转不出来时（没 XSL、没 node、数量对不上、部分转不了）**一律判失败**，
不静默产出混着两种引擎的 Word。

⚠️ **Pandoc 不能从包里去掉**：整个 docx 是它生成的（md→html→docx），
XSL 只是把生成物里的公式替换掉。

XSL 探测：先查注册表（Click-to-Run 和传统 MSI 两种键位都读），再扫常见
目录兜底。本机实测 0.7 毫秒命中——现代 Office 全是 Click-to-Run，
传统那个 `InstallRoot` 键存在但值是空的，只读它会一个都找不到。

## 文字准确度：不做承诺

2026-08-31 实测推翻了初版设计。同一份 PDF 跑 MinerU 三种模式：

| 模式 | 正文字符 | 行内公式 | 「己知」 | 「已知」 |
|---|---|---|---|---|
| txt | 10187 | 131 | 1 | 13 |
| auto | 10187 | 131 | 1 | 13 |
| ocr | 8972 | **213** | 1 | 13 |

那个错字**在原 PDF 的文字层里就是错的**（原书排版打错的字），三种模式都消不掉。
而 txt / auto 丢了 38% 的公式。所以默认 `ocr`。

界面因此不显示「文字版 / 扫描版」这种质量暗示，只报客观事实：
几页、哪几页没有文字层。详见 `docs/DESIGN.md` 第二节。

## 没有显卡能用吗

能。实测（同一份 10 页数学讲义）：

| | 用时 |
|---|---|
| 有显卡（RTX 4060） | 262 秒 |
| 纯 CPU | **460 秒，慢 2.0 倍** |

不是十几倍。10 页的讲义约 8 分钟、30 页的教师版约 23 分钟——晚上挂着转一批
完全可行。所以首启检测到显卡不满足时，界面给的是**具体分钟数**让你自己判断，
而不是「会慢很多」这种废话。

## 给开发者

### 装开发环境

```
.venv\Scripts\python.exe tools\setup_env.py --check   # 看缺什么
.venv\Scripts\python.exe tools\setup_env.py           # 装齐
```

下载约 3 GB（大头是 CUDA 版 torch），装完 `.venv` 占约 5.1 GB。

**注意**：`runtime\pandoc\pandoc.exe`（233 MB）不在版本库里，`.gitignore`
排除了它，`setup_env.py` 也不下载它。从 git clone 出来需要自己放一份
（[pandoc 3.11 发布页](https://github.com/jgm/pandoc/releases/tag/3.11)）。

### 目录

```
pipeline/   probe(体检) gpu(显卡) extract(调MinerU) tomath(XSL公式)
            todocx(出Word) convert(串起来) sources(多源测速)
            paths(落点集中管理) models(模型认领与下载) update(检查更新)
            tex2mml.js(KaTeX 转 MathML) vendor/katex
server/     FastAPI，只绑 127.0.0.1，端口系统分配
app/        Electron 外壳 + 前端（纯 JS 无框架，主屏 + 首次选源屏）
runtime/    pandoc.exe + 许可证
tools/      setup_env(装开发环境) build_release(组装发行版)
tests/      173 条 Python + 61 条前端检查 + 四个真实数据验证脚本
docs/       DESIGN.md（设计与决策台账） RELEASE.md（发行版规矩）
```

### 跑测试

```
.venv\Scripts\python.exe -m unittest discover -s tests -q   # 173 条，8 秒
node tests\front_check.js                                   # 61 条，真渲染
```

这两个都是离线的、秒级的。另有四个**依赖本机真实文件**的验证脚本，
不在自动套件里：

```
tests\real_probe_check.py     真实 PDF 的体检（扫资料库里的 544 份）
tests\real_convert_check.py   拿现成的 MinerU 产物转 Word（11 份，不用 GPU）
tests\real_pdf_to_word.py     端到端：一份 PDF 直接出 Word（要 GPU，约 4 分半）
tests\real_cpu_bench.py       同一份书强制走 CPU，量真实差距（约 8 分钟）
```

它们存在的理由：单元测试用的是脚本造的假数据，只能证明逻辑自洽，
不能证明在真书上做对了。这个项目里已经栽过两次「测试全绿但实际没生效」。

### 发行版

见 **[docs/RELEASE.md](docs/RELEASE.md)**——版本号规则、打包命令、命名规矩、
上传清单、不能破坏的硬约束。**发版前从头照着走一遍**，别凭记忆。

```
tools\build_release.py --version v0.0.1                  组装 + 装依赖
tools\build_release.py --version v0.0.1 --sfx            打成自解压 exe
tools\build_release.py --version v0.0.1 --update-only    只打更新包
```

### 落点：全部在安装文件夹内

**删掉文件夹 = 卸载干净**，不留注册表、不留 AppData。靠三处保证：

| | 靠什么 |
|---|---|
| 模型 / 临时文件 / MinerU 配置 | `paths.child_env()` 的三个环境变量 |
| Electron 缓存 | `app.setPath`，**必须在 app ready 之前调** |
| 转好的 Word | 用户自己选（唯一的例外） |

代价是不能装进 `C:\Program Files`，`paths.writable()` 在启动自检里拦这种情况。

另外**不碰用户的全局 `~/mineru.json`**——那是 MinerU 的全局配置，用户机器上
可能装着别的用 MinerU 的东西，我们通过 `MINERU_TOOLS_CONFIG_JSON` 指向自己那份。
