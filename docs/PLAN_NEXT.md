### 1. ✅ Word 字体：Aptos 换成宋体 + Times New Roman

**2026-09-05 已完成。** 实测产物：标题和正文都是「西文 Times New Roman /
简体中文 宋体」，4 个公式还在、表格边框还在、三个 XML 都能解析。
新增 5 条测试。

**问题从哪来。** 转出来的 Word 正文字体是 Aptos，跟 MinerU、跟本机 Office
版本都无关 —— 它是 pandoc 3.11 自带 reference.docx 的主题字体。实测链条：

项目没有自定义 reference.docx（`todocx.py:317` 明确否掉了这条路，理由是
二进制文件没法审查、没法 diff），所以走的是 pandoc 内置那份。把它导出来解开：

- `word/styles.xml` 的 docDefaults 写着
  `<w:rFonts w:asciiTheme="minorHAnsi" w:eastAsiaTheme="minorEastAsia" .../>`，
  指向主题字体
- `word/theme/theme1.xml` 里 majorFont 是 `Aptos Display`（标题）、
  minorFont 是 `Aptos`（正文），而 **`<a:ea typeface=""/>` 中文是空的**

第二条比 Aptos 本身更值得修：**中文字体压根没指定**，靠 Word 自己回退，
等于不可控。

**目标。** 正文和标题**用同一套字体** —— 中文宋体、西文 Times New Roman，
标题靠 Word 的 Heading 样式（字号 + 加粗）区分。

**为什么不给标题单独设字体。** MinerU 认标题会认错，pandoc 只能照它给的结果转。
正文标题用不同字体的话，认错的地方字体就会跳，出现半页宋体半页黑体的花脸。
统一字体则最多是字号不对，不会花。

**为什么选这两个字体。**

1. 任何 Windows 都有（simsun.ttc / times.ttf，从 Win95 就在）。Cambria、
   Calibri 是**随 Office 装的不是系统自带** —— 本软件要求装 Office，但收
   Word 文件的学生家长不需要装。等线是 Win10 才有，也排除。
2. 跟公式协调。公式是 Cambria Math（衬线体），正文用宋体 + Times New Roman
   同为衬线，段落里插公式不突兀；用微软雅黑那种无衬线会打架。
3. 打印清晰，宋体本来就是为印刷设计的。

**后端。** `todocx.py` 新增 `_set_theme_fonts(docx_path)`，跟现有
`_add_table_borders()` 并列调用 —— 同样是解 zip、改 `word/theme/theme1.xml`、
塞回去。XML 里同时写好备选（宋体 → 微软雅黑），别只写一个。

**前端。** 无。

**对现存代码的影响。** 只新增一个函数加一处调用。不碰 pandoc 参数、不引入
reference.docx。

**对版本更新的影响。** 无。纯转换逻辑，跟更新链路无关。老版本转出来是 Aptos、
新版本是宋体，已转好的文档不受影响。

**已知限制。** 公式仍是 Cambria Math，Word 强制的，改不了。正文改完之后公式
里的字母还是那个样子，这不是没改干净。

### 5. ✅ 缓存扫描与清理

**背景。** `pip cache info` 实测本机 **4125.4 MB / 1462 个文件**，全是下载缓存
（本地构建的 wheel 是 0 个）。用户永远发现不了它，有三层遮挡：

1. AppData 是隐藏文件夹，资源管理器默认不显示
2. 文件名是哈希，`140d28266e23cac4...`，看不出是什么
3. 扩展名是 `.body` 不是 `.whl`，双击打不开，搜「whl」也搜不到

**已定：缓存留在 C 盘原位置，不改 PIP_CACHE_DIR**（理由见决策台账）。但
**必须在环境检测里显示出来**，否则这几个 G 就是用户永远解不开的谜。

**必须列明细，不能只给一个总数加清理按钮。** 实测扫出来的内容：

```
2625.6 MB   torch-2.11.0+cu128        本软件的
 230.3 MB   onnxruntime_gpu-1.28.0    本软件的（mineru 依赖）
 160.4 MB   pyside6_addons-6.11.2     不是本软件的
 116.4 MB   torch-2.13.0              不是
 116.3 MB   torch-2.13.0+cpu          不是
  73.3 MB   pyside6_essentials-6.11.2
  42.0 MB   opencv_python-5.0.0.93
  39.9 MB   llvmlite-0.48.0
  34.9 MB   scipy-1.18.0
```

PySide6 是小蔡自己那个 Qt 项目（金石工作台）下的，torch 2.13.0+cpu 也是别的
项目的。**pip 缓存是按 Windows 用户走的，不是按 Python 环境** —— 开发环境的
`.venv`、发行版的 embeddable Python、别的项目全往同一个目录塞。一键清理会误伤。

**判断谁是谁。** 本软件用的包名是已知的（`DEPS` 清单加 torch/torchvision），
版本还要对得上 —— `torch-2.11.0+cu128` 是我们装的，`torch-2.13.0+cpu` 显然不是。

**技术要点，都实测过：**

| 问题 | 答案 | 证据 |
|---|---|---|
| 缓存目录在哪 | **必须问 `pip cache dir`**，不能硬编码 | 实测把 `PIP_CACHE_DIR` 指到别处，`pip cache dir` 的输出立刻跟着变。硬编码遇到改过的用户会显示 0 字节，而他 C 盘明明被占着 |
| 怎么读出包名 | 每个 `.body` 是 zip，读它的目录找 `*.dist-info/` | 实测扫 731 个 `.body` 秒级完成（只读 zip 目录不解压）。注意 pip 报的 1462 个文件是 731 个条目乘 2，每条都有 `.body` 和 `.metadata`，**只需要扫 `.body`** |
| `pip cache list` 能用吗 | **不能**，它只列本地构建的 wheel，那 3.9 GB 一条都不列 | 实测输出 `No locally built wheels cached.` |
| 删得动吗 | 能，普通用户权限就够 | 探针测试：能写入、能删除，且 `IsUserAnAdmin()` 是 False |
| 删单个安全吗 | 安全，没有索引文件 | `http-v2/` 下只有 0 到 f 十六个分桶目录，根层没有任何文件。删掉某个缓存文件，pip 下次重新下载 |

**三个边界情况：**

- **文件正被占用**（后台正在装 torch）：逐个删，失败的记下来，老实报「清了
  3.7 GB，1 个文件正在使用没删掉」，**不假装全成功**
- **以管理员身份运行时**，`%LOCALAPPDATA%` 指向管理员账户，看到的缓存跟用户
  平时用 pip 的不是同一个 → 诊断报告里加一行「当前以管理员身份运行」
- **转换进行中禁用清理**，跟「检查更新」一个规矩

**后端。** 新模块 `pipeline/maint.py`。

**对版本更新的影响。** 新文件放 `pipeline/`，而 `UPDATE_PARTS` 里是**整个
目录**，新文件自动进更新包，不用改打包清单。

### 7. ✅ 依赖升级（复选框、备份、回滚）

这是最重的一块。

**流程：**

```
1. 读策略（requires.json 的 upgrade 段）
     写了 ok:false  -> 显示理由，没有勾选框，到此为止
     没写 / ok:true -> 出现勾选框
2. 用户勾 torch / mineru，点升级
3. 先跑 pip --dry-run --report（不真装），算出：
     · 实际会动哪些包，各从几号到几号
     · 要下载多少
   如果发现会动到用户没勾的包 -> 停下来摆给他看，让他确认或取消
4. 算备份大小、查剩余空间；不够就明说缺多少
5. 备份要动的包
6. 执行升级
7. 成功 -> 提示重启；备份留着，出现在环境检测的清理列表里
8. 中途断电 -> 下次开机无条件回滚（见下）
```

**关键技术选择一：用约束文件，不用 `--no-deps`。**

mineru 的包里自带一行机器能读的声明：`torch<3,>=2.6.0`。用户只勾了 mineru
时，pip 解依赖完全可能顺手把 4.2 GB 的 torch 也换掉。两种堵法：

- `--no-deps`：强行只装 mineru 不管依赖。风险是新版 mineru 真需要新 torch 时，
  装完直接 import 失败
- **约束文件**：把没勾的包钉在当前版本交给 pip，pip 解不出来就**报错**

第二种更好，它让冲突**显式暴露**，而不是装出一个坏组合。配合第 3 步的
dry-run，用户在按下去之前就知道「这两个升级是打架的」。

**关键技术选择二：安装放在重启时做，运行时全程不打扰。**

```
下载阶段（几十分钟）  后台跑，用户照常转 PDF，一点不受影响
        下完了
提示「新版本已下载，重启后生效」   不装，只提示
        用户什么时候想重启就什么时候点
重启 -> 进主界面之前装（几分钟，有进度条）-> 正常进入
```

⚙ **2026-09-05 复查修正 —— 原计划这里有个自相矛盾。** 说「下载后台跑、安装
放重启时」，但同时又定了「完全用 pip」，而 `pip install` 是下载加安装一体的，
**分不开**。这两条原本是打架的。

解法是用 pip 自己的两个命令，仍然一行自研下载代码都不写：

```
第 1 步（后台，不拦人）
  pip download -d <cache目录> -c <约束文件> mineru==3.6.0

第 2 步（重启时，很快，不联网）
  pip install --no-index --find-links <cache目录> mineru==3.6.0
```

`--no-index` 让第 2 步完全不联网，只用本地下好的 wheel，所以重启时那几分钟
只是解压和搬文件，不会卡在网络上。

⚠️ **约束文件必须在下载阶段就用上**，否则下下来的可能是错的组合，到安装时
才发现就晚了。

⚠️ 这两条命令都实测确认存在（`pip download -d/-c`、`pip install --no-index
--find-links`），但**没在发行版那个 embeddable Python 上验过**，跟
`--dry-run --report` 一起进待验证清单。

这跟现有的软件更新流程完全一致（下载、提示重启、重启时应用），用户不用学新
东西。安装放在重启时的理由：那个时刻本来就没有转换任务在跑，天然不打扰任何人。

**关键技术选择三：断电了不判断，无条件回滚。**

这一条是整块设计里最要紧的。**pip 没有事务**，它装一个包分四步：

```
1. 解压 wheel 到临时目录
2. 卸载旧版（删文件、删 dist-info 里的 RECORD 清单）
3. 把新文件搬进 site-packages
4. 写新的 RECORD 清单
```

断电停在哪一步，后果完全不同：

| 断在 | 现场是什么样 | 重跑 pip 能修好吗 |
|---|---|---|
| 第 2 步（卸载中） | 旧版清单已删，文件还剩一半 | **不能**。pip 看不到清单，以为没装过，直接装新的，**剩下的旧文件没人清理**，新旧混在一个目录里 |
| 第 3 步（搬文件中） | 新文件到位一半，清单还没写 | 能 |
| 第 4 步（写清单中） | 文件全在，清单不全 | 表面能，但以后卸载会卸不干净 |

**壁垒不在「修不修得好」，在于我们根本不知道它断在哪一步。** 更糟的是：torch
有几万个文件、37 个 dll。新旧混着的时候 `import torch` **可能是成功的**——
直到用户转到某一页调用了那个缺失的算子才崩。**「import 通过」完全不能证明
环境是好的。**

所以做法是在 pip 外面自己套一层事务：

```
1. 装之前，把要动的包完整备份（torch 目录加它的 dist-info）
2. 写状态文件：{阶段:"安装中", 动了谁:["torch"], 备份在:"backup/0904_2130"}
3. pip install
4. 成功 -> 状态文件标成完成，备份留着（进环境检测让用户清）
5. 断电 -> 下次启动读到「安装中」-> 把 site-packages 里那几个包整个删掉，
          从备份原样拷回去 -> 状态清空 -> 正常进主界面
```

**第 5 步「无条件」三个字是关键。** 不检查坏没坏、不判断断在哪、不试图修补 ——
现场多乱都无所谓，删干净再拷回去，得到的一定是升级前那个能用的版本。回滚本身
再断电也不怕：删加拷这个动作重复做多少次结果都一样，备份还在原地。

这跟「不拦人」不冲突：整个回滚是开机时自动做的，用户看到的就是启动慢了两分钟，
进度条写着「正在恢复上次未完成的升级」，然后正常进主界面。不弹框、不问他、
不需要他做任何决定。

**第一版备份用真拷贝，不用硬链接。** 硬链接实测很快（8 MB 文件 0.0007 秒，
删掉源之后备份还在），备份 4.2 GB 的 torch 也是瞬间。但它成立的前提是
「pip 卸载时是删文件，不是原地改写文件内容」—— 如果是后者，备份那份会跟着
一起变，**等于没备份**。这个前提没在真机验证过，而备份是最不能出错的地方。
**先做对，再做快**：第一版老实拷贝（4.2 GB 几分钟，有进度条），等验证过
pip 的行为再换硬链接提速。

**升级后不做自检。** 原本设计是内置一个小 PDF、升级后真转一遍验证。撤销了，
理由是小蔡说的两条：让用户等很久（要加载模型，30 秒起步），而且**显得对软件
不自信**——正常软件升级完不会说「让我先测测我还能不能用」。

改成**不主动测，出事才兜底**：升级之后什么都不做，正常进主界面。如果用户
升级后第一次转换失败了，才提示「这是升级后第一次转换，可能跟升级有关，
要不要撤回到升级前」。

**后端。** `pipeline/deps.py` 里的升级逻辑。

**前端。** 环境检测页；dry-run 的结果默认折叠，只显示「将升级 mineru
3.4.5 到 3.6.0」，「详情」展开完整清单（一次升级动十几个包很正常，
全摊开会吓着人）。

**对现存代码的影响。** 新增为主，**但要加一条互斥**：升级依赖时禁用「检查
更新」，反之亦然。现在只有「转换中禁用检查更新」这一条。

**对版本更新的影响。** 备份目录和状态文件都是新增的，老版本不认识也不会去读。
唯一风险是用户升级依赖后又把软件降级回老版本，备份目录会成孤儿（占硬盘但没
人管）。概率极低，而且环境检测里能看到能删。

### 8. ✅ requires.json 加 upgrade 段

**这一段是什么。** 一小段文字，跟着每次发布挂在 GitHub 上，软件读它来决定
要不要给用户升级按钮。

**默认什么都不用写。** 般配度不用人管 —— mineru 的包里自带
`torch<3,>=2.6.0` 这样的声明，`pip install --dry-run` 一跑就知道配不配得上，
配不上直接报错。**不需要实测。**

于是三种情况全部自动覆盖：

| 情况 | 谁来判断 |
|---|---|
| 只升 mineru，会不会连累 torch | pip 解依赖，dry-run 提前告诉你会动谁 |
| 只升 torch，mineru 认不认 | pip 拿 mineru 的声明去比，不合直接拒 |
| 两个一起升，配不配 | 同上，pip 一次解完 |

**upgrade 段只是个可选的黑名单**，用于 pip 查不出来的那类问题（比如新版
识别率掉了）：

| 写了什么 | 用户看到 |
|---|---|
| **什么都没写**（默认） | 「上游有 2.14.0，我们没测过，升不升你自己定」加升级按钮 |
| `ok: false` 加理由 | 你的理由，**不给按钮** |
| `ok: true` 加理由 | 「实测可升」，按钮变推荐样式 |

**这个设计有个好处：你停止维护之后它仍然正确。** 新版本自动落进「没测过」，
不会假装有结论。

**torch 那条要按通道分开写。** 这是个硬约束：你的策略结论是在**你自己那台
cu128 机器**上测出来的，但驱动 525 到 569 的用户走 cu126 通道，**那条通道上
的 torch 是另一个包**（里面打包的是 CUDA 12.6 的库）。cu128 上测通过不能
证明 cu126 上也行。所以：

```json
"torch": {
  "cu128": { "ok": true,  "to": "2.12.0", "note": "本机实测通过" },
  "cu126": { "ok": null,  "note": "" },
  "cu118": { "ok": null,  "note": "" }
}
```

你测哪条写哪条，没测的自动落在「没测过，用户自己定」。**不把一台机器的结论
套到所有人头上。** mineru 不用分通道（纯 Python 包，跟 CUDA 无关）。

用 `null` 而不是「干脆不写这一项」：不写分不清是忘了还是没测，写 null 是明确
表示「这一项存在但没测」，打包门禁可以据此提醒。

**后端。** `build_release.py` 生成时预留这一段；`update.py` 读取。

**对现存代码的影响。** `requires` 那一段**一个字不动**，只在旁边加一段。

**对版本更新的影响 —— 这是全部改动里兼容性最关键的一处，而且天然安全。**
`check_requires()` 用的是 `json.loads(raw).get('requires')`，**只取这一个键**，
多出来的键它根本不看。所以 v0.0.2 那个老客户端拿到新格式 json 照常工作。
反过来，新客户端拿到老 Release 的 json（没有 upgrade 段）读不到就当「没测过」。
**双向兼容，不用做版本协商。** 但要补个测试把这条锁住，免得以后有人改坏。

### 11. ✅ SFX 安装包配置修正

**2026-09-05 已完成。** 六个不生效的字段全删了，`BeginPrompt` 改成直接
告诉用户「默认填的是安装包所在文件夹，请改掉」，那条写反的注释也修了。
生成的配置已验证：三个官方字段都在、六个无效字段全无、引号成对。

**这是个从 v0.0.1 就存在、一直没人发现的问题。**

**现象。** 安装包的默认路径是**安装包自己所在的目录**。从浏览器下载后双击，
默认就填下载文件夹。实测小蔡把 exe 放在 `D:\浏览器下载文件`，默认路径就是
那里。

**危害。** 下载文件夹是很多人定期清理的地方。一清就把软件连同 4.6 GB 模型
一起删了，而老师大概率不会去改这个路径 —— 弹窗里已经填好了一个看起来合理的
路径，谁会去改。

**根因。** 项目用的是 `7z.sfx`，这是 7-Zip 官方的**普通解压模块**。而
`InstallPath`、`GUIMode` 这些是 `7zSD.sfx` / `7zS.sfx`（**安装器模块**）
才支持的字段。官方 7z.sfx 只认这几个：`Title`、`BeginPrompt`、`Progress`、
`RunProgram`、`Directory`、`ExecuteFile`、`ExecuteParameters`。

配置里另外六个字段**全部被静默忽略**：`InstallPath`、`GUIMode`、
`OverwriteMode`、`ExtractPathText`、`ExtractTitle`、`ExtractDialogText`。

验证方式：把六个安装包的 SFX 配置段从 exe 二进制里解出来核对，全都写着
`InstallPath="D:\PDF2Word"`，而实际行为是用 exe 所在目录。

**顺带查出注释里还有个错**（`build_release.py:525`，字段本身在 536 行）：

> `# GUIMode=2 是「问用户解压到哪」，正是普通安装包的体验。`

在支持它的安装器模块里，`GUIMode="2"` 的意思是**完全隐藏解压对话框（静默
模式）**，跟注释说的正好相反。幸好这个字段在 7z.sfx 上被忽略，没造成实际
后果，但注释是错的，会误导下一个改这里的人。

**做法（A 方案）：**

1. 删掉六个不生效的字段。**留着比不写更糟** —— 它让人以为设过默认路径了
2. 改 `BeginPrompt` 文案，把这件事直接讲给用户：

```
要把「PDF 转 Word」安装到哪里？

下面默认填的是这个安装包所在的文件夹。如果你是从浏览器下载的，
那就是「下载」文件夹 —— 请改掉，否则哪天清理下载文件夹，
会把整个软件连同 4.6 GB 模型一起删掉。

建议填：D:\PDF2Word

请不要选 C:\Program Files —— 那个位置写不了文件。
路径里可以有中文、空格和括号。
所有文件都会留在这个文件夹里，不想用了直接删掉即可。
```

3. 修正那条错注释，并写明这六个字段为什么不能用，免得下次有人加回来

**对版本更新的影响。** 无。安装包和更新包是两条完全独立的路 ——
`apply_update()` 只认 `paths.ROOT` 这个目录结构，不认它是怎么来的。

### 1. ✅ 查版本的并发是「假并发」（2026-09-05 已修）

**现状**（`update.api_race`）：

```python
with futures.ThreadPoolExecutor(...) as ex:
    for i, (m, d, e, ms) in enumerate(ex.map(one, API_MIRRORS)):
        if d is not None and data is None:
            data = d          # 取名单顺序第一个成功的
```

六条**确实同时发出去了**，但 `for` 循环必须走完六个结果才结束。

**后果**：直连排第一，它不通的网络里每次检查更新都要等满 6 秒 ——
即使某个镜像 1 秒就返回了。而这个软件的目标用户（老师的电脑）大概率
直连不通。

⚠️ 源码注释里写着「并发之后，最坏耗时 = 最慢那条的超时，典型情况约
1.5 秒」—— **那句话只在直连能通时成立**。写注释时是在能直连的环境下
测的。

**改法**：`ex.map` 换成 `as_completed`，拿到第一个成功的就 break。

- 直连通的环境：还是用直连（它最快），行为不变
- 直连不通的环境：第一个成功的镜像立刻用上，不等那 6 秒

**不改任何策略**，只是把「等所有人跑完再按名单挑」换成「谁先成功用谁」。

代价是线路明细会不全（提前 break 了）。两种处理：拿到数据立刻返回、
明细标注「其余线路仍在检测」；或者后台把剩下的跑完再补明细。倾向前者 ——
明细是给排查用的，用户点「线路 ▾」展开时再补也不迟。

🔴 **这一条后来被自己推翻了（2026-09-05 同日，见第十一章末节）。**
「拿到数据立刻返回、明细标注仍在检测」这个倾向选错了：明细不是只给排查
用的，它就摆在主界面上，用户第一眼看到的是「1/6 条可用」。而且前端压根
没接 `pending` 字段，于是「仍在检测」根本没显示出来，直接写成了「连不上」。
最终改回 v0.1.1 的「六条一起等」，另加一个总时间上限。

### 2. ✅ 模型上游更新了，用户没有任何办法更新（2026-09-05 已做）

**这是这轮做的功能留下的缺口**：`deps.check_models()` 能查出上游更新了

### 6. 依赖升级的下载阶段没有进度条（2026-09-05 发现，**2026-09-06 定：要做 → 见第十八节**）

`upgrade.download()` 的签名里有 `on_progress`，但**从签名之后再没出现过**：

    upgrade.py:288   def download(picked, targets=None, on_log=None, on_progress=None):
    upgrade.py:310       rc, out = _pip(argv, timeout=7200, on_log=on_log)   ← 没往下传
    _pip() 内部          没有 --progress-bar raw，只有逐行 on_log
    server/main.py       6 处 on_progress=on_prog 全是别的模块，没有一处给 upgrade

结果：升 torch 要下 2.7 GB、几十分钟，界面上只有滚动日志，**没有进度条**。

**为什么算问题。** 跟项目的既有规矩正面冲突 ——「任何耗时操作都不给黑盒」。
而且同一个软件里 `torchdep.install` 早就做对了（`--progress-bar raw` +
`ProgressAcc` + 进度条），升级这条路是**同一件事长成了两个样子**。

**怎么改**（三处）：

1. `_pip()` 加 `--progress-bar raw`，把 `parse_progress()` 认出来的行喂给
   `on_progress`、不进日志区 —— 照抄 `torchdep.install` 的形状，那边的
   `is_noise()` 就是干这个的（2.7 GB 会刷几千行进度，不拦会把
   Collecting / Downloading 这些真正有用的行全淹掉）
2. `download()` 把 `on_progress` 真的传下去
3. `server/main.py` 的升级任务接上 got/total，前端加一屏进度

**分母怎么来。** `pip download` 的输出格式跟 `pip install` 一样，直接复用
`torchdep.ProgressAcc`（2026-09-05 已改成分母跟分子同源、只增不减）。
🔴 **不要再写一个估算常量** —— 92% 那次事故就是估算常量惹的：照着 pip 打印的
十进制 MB 换算成 MiB 当分母，下完了进度条只走到 92%。

**为什么现在不做。** 改动跨后端两个文件加前端一屏，比这一批其他几项都大。
小蔡 2026-09-05 定「依赖升级先不管，主要改更新那一块」。

## 四、决策台账（否掉了什么，为什么）

这一节记的是**讨论过但没采纳的方案**。写下来是为了不重复讨论。

### 否掉：锁死 torch 版本（或用 `~=` 锁次版本）

**提议是什么。** 在通道表里给每条通道钉一个 torch 版本，让所有用户跑同一个
版本 —— 也就是小蔡实测过的那个。

**为什么否掉。** 小蔡一句话点破：「你又不是英伟达」。锁版本等于赌
「PyTorch 不会再往 cu128 发新版」，而那只是今天观察到的一个现象，不是永久
事实。万一他们恢复更新，锁死的用户就被关在门外了。

还有一层：**软件哪天不维护了，「取通道内最新」仍然能自己工作，锁死的版本
反而会因为源上删包而装不上。不锁比锁更耐放。**

**那版本不统一怎么办。** 不消除差异，**把差异显示出来**（环境检测的三列
对比）。让用户和开发者都看得见自己跑的是什么版本。

**保留现状：** 查驱动、匹配通道、取通道内最新。一个字不改。

### 否掉：自己写断点续传下载器

**提议是什么。** torch 那 2.75 GB 用 pip 下不支持断点续传，下到 90% 断网就
得重来。提议自己下（HTTP Range），下完再 `pip install 本地文件`。

**为什么否掉。** 三条理由：

1. 少写一个下载器就少一个出错的地方。断点续传要处理：半截文件怎么记、服务器
   不支持 Range 怎么退化、文件被人动过怎么办、多次续传后哈希对不上怎么办 ——
   全是自己的新 bug 来源，而 pip 那条路已经被全世界跑了十几年
2. 判断、下载、安装在一个工具里，行为一致，出问题不用先分清是谁的锅
3. **最关键：没有数据支持「下载经常中断」这个假设。** `logs/` 里**只有
   `convert.log`，没有 `torch_install.log`** —— 这条安装流程在开发机上从没
   真跑过，一次失败记录都没有。是在为一个还没被证实存在的问题写代码

**那断点续传怎么办。** 先不做，等有真实失败数据再说。`torchdep.install()`
已经有完整日志，真有用户反复下不下来，日志里看得见。到那时才知道是「网断了」
还是「源太慢超时」，方案才有针对性。

**顺带记一笔：这条路技术上是通的**，验证都做完了，将来要做直接用：

- PyTorch 源支持断点续传：`HTTP 206`，`Content-Range: bytes 0-99/2753189216`
- **不用自己判断该下哪个文件**：`pip install --dry-run --report` 会给出精确
  地址和 sha256，只花 29 KB。判断仍由 pip 做，我们只接手「下载」这个动作
- wheel 链接自带校验值，`_fetch_one()` 那套三道验证可以直接套上

### 否掉：单独一个 policy.json

**为什么。** 已经有 `requires.json` 跟着每个 Release 走，还有现成的 gh-proxy
三线路拉取逻辑。多一个文件就要多一套下载代码。并进 `requires.json` 加一段就行。

### 否掉：requires.json 里加 runtime 段

**提议是什么。** 记「这一版实测过的运行时版本」，给环境检测做对比基准。

**为什么否掉。** 不锁版本之后，「我们测过什么」这个说法本身就不成立 —— 只
可能测自己那台机器那条通道。而且「应该装什么」已经写在代码里的
`TORCH_CHANNELS` 常量中，读常量就行，不必多存一份还得同步。

### 否掉：底栏按钮按状态切换文字

**提议是什么。** 平时显示「关于」，环境自检没过或卡在下载安装屏时自动变回
「检查更新」，让卡住的用户一眼看到出口。

**为什么否掉。** 小蔡要行为统一：处处都显示「关于」。风险可控 —— 用户卡住时
主区被 `gateKind` 拦着，底栏那个「关于」是当时唯一能点的东西，而进去第一个
按钮就是「检查更新」。

**代价**：自救路径多一层点击。**换来的前提是每一屏底栏都真有这个按钮**，
所以进了待验证清单。

### 否掉：安装中断电时弹框问用户

**为什么。** 小蔡定的是「不拦人就贯彻到底」。改成不问，开机自动回滚。用户
看到的只是启动慢了两分钟，进度条写着「正在恢复上次未完成的升级」。

### 否掉：第一版就用硬链接备份

**为什么。** 硬链接实测很快（8 MB 文件 0.0007 秒），但它成立的前提是「pip
卸载时是删文件不是原地改写」，这个前提没在真机验证过 —— 而备份是最不能出错
的地方。第一版老实真拷贝，验证过再换。

### 否掉：升级后自动转一份测试 PDF 做自检

**为什么。** 小蔡的两条理由都成立：让用户等很久（加载模型 30 秒起步），
而且**显得对软件不自信**。改成「不主动测，升级后第一次转换失败才提示回滚」。

### 否掉：加 cu129 / cu130 / cu132 通道（**2026-09-06 翻案：全加，但有条件 → 见第十八节**）

**为什么。** 加了之后**一部分用户会拿到更旧的 torch**。

通道表是从上往下第一个匹配就返回。按 cu 号从大到小排的话，一个驱动 578 的
用户会这样走：cu132 够不着、cu130 够不着、cu129 够得着，停在 cu129 ——
**而 cu129 只发到 torch 2.9.0**，比 cu128 的 2.11.0 还旧。不加通道他本来
能落到 cu128 拿 2.11.0。

根源还是那个老毛病：**cu 号大不等于版本新**。cu129 是个短命通道。

另外，小蔡自己的驱动是 572.83，**连 cu129 要求的 576.02 都够不上**，加了
这几条通道他自己一条都匹配不到，等于加了个永远测不到的东西。

**真要加的话，通道选择逻辑得跟着改** —— 不能「第一个够得着就用」，得
「够得着的里面挑 torch 版本最高的」。但那会把大批用户从 cu128 挪到 cu126，
动静比加通道本身大得多。

**改为：** 打包门禁里加一条检查，发现官方出了新通道就提醒一次，加不加人来定。
不主动加，也不装作没看见。

### 否掉：换第三方 SFX 模块（B 方案）

**提议是什么。** 换成 `7zSD.sfx`（支持 `InstallPath`），真正解决默认路径问题。

**调研结果：**

| | star | 最后提交 | 最新发布 | LICENSE |
|---|---|---|---|---|
| chrislake/7zsfxmm | 69 | 2020-05-13（6 年前） | 2017-06-15（9 年前） | LGPL-3.0 |
| cosmomill/7zsfx | 1 | 2017-04-17（9 年前） | 无 | **没有 LICENSE** |

`cosmomill/7zsfx` 直接排除 —— 没有 LICENSE 等于保留所有权利，法律上不能用。
`7zsfxmm` 的 LGPL-3.0 跟 GPL-3.0 兼容，但九年没发新版。

**六项影响，按严重度排：**

1. **杀软误报风险上升**。自解压包本来就容易被杀软盯上，第三方修改版的 SFX
   模块误报率更高。而 exe **本来就没有代码签名**，已经会触发 SmartScreen
   「未知发布者」，换成第三方模块可能从警告变成直接拦截
2. **引入一个 9 年没更新的二进制**，它会跑在每个用户机器上。基于 2017 年的
   7-Zip（16.x/17.x），而现在打包用 7-Zip 26.02。老模块解不解得开新版压出来
   的 .7z 要实测；当年的 CVE 修复不在里面；出问题没人修
3. **打包机上多一个依赖**。现在 `find_7z()` 只找系统装的 7-Zip，7zSD.sfx 得
   自己带进仓库（多个不可审查的二进制）或写下载步骤（打包依赖外网）
4. **分发义务多一条**。LGPL-3.0 要求附许可证和版权声明
5. **老用户重装时体验会变**
6. `check_package.py` 可能要跟着改

**已装用户的更新完全不受影响**（`apply_update()` 不认安装方式），但上面六条
不值得为「设个默认路径」付出。

### 否掉：换 Inno Setup（C 方案）

**为什么。** 三个新问题：

1. **跟「删文件夹就干净」冲突**。Inno 的卸载程序只删它装的时候记录过的文件，
   而运行中产生的模型 4.6 GB、日志、appdata、_tmp 全不在记录里，**卸载后原样
   留着**。反而比现在的「直接删文件夹」更脏，正好打在核心承诺上
2. **默认路径要专门配**。Inno 默认往 `C:\Program Files\` 装，而这软件恰恰
   不能装那儿
3. **两批用户状态不同**。老用户 SFX 装的（注册表干净），新用户 Inno 装的
   （有卸载项）

为了设个默认路径把整个分发模型换掉，还捎带破坏最在意的规矩，不划算。

### 否掉：把 pip 缓存改到安装目录（PIP_CACHE_DIR）

**提议是什么。** DESIGN 里标红的待办：pip 缓存漏在用户 AppData，违背「删掉
文件夹等于卸载干净」。提议在 `paths.child_env()` 加 `PIP_CACHE_DIR` 指进
安装目录（**已验证 `torchdep.py:642` 装 torch 走的正是这个 env，加一处就够**）。

**为什么否掉。** 小蔡的判断：留在 C 盘，万一别人用得上。

**而实测证明这个判断是对的** —— 缓存里扫出 `pyside6_addons` 160 MB、
`pyside6_essentials` 73 MB，那是他自己金石工作台那个 Qt 项目下的；还有
`torch-2.13.0+cpu` 也是别的项目的。**pip 缓存按 Windows 用户走，不按 Python
环境走**，他自己就是「别人用得上」的那个人。

**代价：** README 里「不留 AppData」那句成了假话，要改（见改动 12）。

### wheel 是什么

`.whl` 就是个 zip 换了后缀名。实测下一个小包解开：

```
filelock/__init__.py               真正干活的代码
filelock/_api.py
...
filelock-3.32.5.dist-info/METADATA    这包叫什么、要什么 Python、依赖谁
filelock-3.32.5.dist-info/WHEEL
filelock-3.32.5.dist-info/RECORD      这个包装了哪些文件的清单
```

`pip install` 干三件事：下载那个 zip、解压搬进 site-packages、把 dist-info
也搬进去当「装过了」的凭证。**卸载时 pip 就是照着 RECORD 这张清单一个一个
删** —— 这解释了断电为什么难修：清单删了但文件没删完，pip 就再也不知道该
清理谁了。

## 六、动手前必须实测的四件事（2026-09-05 **四条全验过**）

这四处最容易自欺，验不过对应的设计就要换做法。结果：

| | 结论 |
|---|---|
| 1. 发行版 pip 支不支持 `--dry-run --report` | ✅ **支持**，实测是 pip 26.2.1 |
| 2. 硬链接备份成不成立 | ✅ **成立**，所以备份 4.2 GB 的 torch 是瞬间的 |
| 3. 字体改完 Word 还能不能打开 | ✅ 真讲义端到端 + 四种边界 + 发行版 Python 都过 |
| 4. 每屏底栏是不是都有自救入口 | ✅ 前端检查里 14 个屏的断言都改成守 `openAbout` 了 |

### 1. ✅ 发行版的 pip 支不支持 `--dry-run --report`（已验：支持）

开发环境是 pip 26.2.1 没问题，但**发行版是 embeddable Python 用 `get-pip.py`
装的**，版本未必一样。`--report` 要 pip 22.2 以上。

**不支持怎么办**：退化成「不预览、只警告」，不能让整个升级功能废掉。

### 2. ✅ 硬链接备份在 pip 升级之后还成不成立（已验：成立）

**2026-09-05 真跑了一遍**：装 filelock 3.20.0 → 硬链接备份一个文件 →
升级到 3.32.5 → 读备份那份，**仍是旧内容**。

所以 pip 是「删文件重写」不是「原地改内容」，硬链接备份成立 ——
备份 4.2 GB 的 torch 是瞬间完成的，不用拷几分钟。

（`upgrade._backup_one` 里先试 `os.link`，跨盘之类失败了退回
`shutil.copy2`，两条路都通。）

以下是当初的分析，留着当台账：

前提是「pip 卸载时删文件，不是原地改写文件内容」。如果是后者，备份那份会跟着
变，**等于没备份**。

**怎么验**：拿 torch 真跑一次 —— 硬链接、pip 升级、检查备份那份还是不是旧版本。

**不通过怎么办**：退回真拷贝（慢几分钟但一定对）。第一版本来就用真拷贝。

### 3. ✅ 字体改完之后 Word 还能不能正常打开（2026-09-05 已验）

**为什么它排在最前面**：`_set_theme_fonts()` 改的是 docx 内部的
`word/theme/theme1.xml`，改坏了 Word 会报「文件已损坏」，而这是
**每一份转换产物都会经过的路径** —— 比另外三条更该先验。

**验过了，三种方式都过：**

- **真实讲义端到端**（5 个公式 1 个表格）：产物 zip 完整、公式表格边框
  都在、`document.xml` / `theme1.xml` / `styles.xml` 三个关键 XML
  都能被 lxml 解析。对比历史产物：改动前是「Aptos Display / 等线 Light」，
  改动后是「Times New Roman / 宋体」
- **边界情况**：没有 theme 的 docx 返回 0 且不动文件；theme 缺 Hans 行时
  只改 latin 不硬塞；连跑两次结果一致（幂等）
- **拿发行版那个 embeddable Python 跑过**（不是开发环境的 .venv，
  RELEASE.md 专门警告过这两者不是一回事）：两组字体都改对，
  Aptos 和等线各剩 0 处

**另外加了一层保护**：字体改失败**不会**让整份转换失败 —— 走到那一步
公式表格都已经转好了，字体只是锦上添花，磁盘满了、文件被杀软锁了这类
意外，宁可让用户拿到一份 Aptos 字体的 Word，也不能让他一无所有。
失败原因记在 `rep['theme_fonts_error']` 里，不静默吞掉。有测试锁住这个行为。

### 4. ✅ 每一屏底栏是不是都真的调用了 `botBar()`（已验）

前端检查里那 14 个屏的断言原本守的是 `data-act="checkUpdate"`，
现在改成守 `openAbout` —— **不是放宽，是换守护对象**，规矩没变：
每一屏都要有自救入口。另外新增两条把改名的代价补上：
「关于页里第一个按钮就是检查更新」和「环境检测页没查过上游时
不能写已是最新」。

「处处显示关于」的前提是每一屏都有这个按钮。`botBar()` 是公共函数，但要逐屏
核对，不能有哪个错误屏是死路 —— v0.0.1 就是栽在「下载屏底部没有这个按钮」。

## 八、版本兼容性总表

**结论：所有改动对「任意版本到任意版本」的更新都是安全的。**

| 兼容方向 | 情况 |
|---|---|
| 老客户端拿到新 Release | `check_requires()` 只读 `requires` 键，新增的 `upgrade` 段它看不见也不受影响。v0.0.2 照样能更新到 v0.2.0 |
| 新客户端拿到老 Release 的数据 | 读不到 `upgrade` 段就当「没测过」，读不到 `last_run.json` 就显示「暂无记录」。**都要写成缺失即降级，不能抛异常** |
| 新增的代码文件 | `pipeline/` 和 `app/renderer` 在 `UPDATE_PARTS` 里是**整个目录**，新文件自动进更新包，不用改打包清单 |
| 依赖清单 | 这批改动**不新增任何 pip 包**（全用标准库 os / zipfile / json / shutil），`requires.json` 内容不变，不会触发「依赖不满足」拦住老用户 |
| 安装包形式的改动 | 安装包和更新包是两条独立的路，`apply_update()` 只认目录结构 |

**唯一需要留神的一处**：改动 9 要在转换主流程里插一次写文件。那是全项目最不能
出错的路径，一个 try/except 包住，写失败就跳过，**绝不能让记日志把转换搞崩**。

### 改了四处

**1. `maint.note_run()` 字段名对不上（真 bug，有实证）**

pip 坏了、`pip_cache_dir()` 返回空串时，白名单就从「pip 缓存目录」

abspath：问不出来就一个都不删。

原有的 `test_只删缓存目录里的东西` 盖不住这个形状 —— 它跑的时候
`pip_cache_dir()` 是有值的。新增 `test_问不出pip缓存目录时不能退化成删当前目录`。

`extract` 改成 `run()` 外壳兜底 + `_run_inner()` 干活，跟
`server._work / _work_inner` 同一套写法。`sources.download` 那两处
就地包 try。

**4. `app/package.json` 版本号落后一版**

## 十、v0.2.1：复查发现的六处（2026-09-05）

第九章那轮全量审查之后，小蔡要求再查一遍并把发现的都处理掉。这一章记
改了什么、什么没改、为什么。

### 改了六处

**1. 删掉 5 处死 import**

`convert.py` 的 `os`、`upgrade.py` 的 `re`、`check_claims.py` 的 `re`、
`make_icon.py` 的 `ImageChops`、`test_maint.py` 的 `json`。都确认过
`名字.` 在文件里出现 0 次。`make_icon.py` 那个是
`from PIL import Image, ImageChops, ImageDraw` 一行里的第二个，改的是
这一行而不是删整行。

⚠️ 动手时踩了个坑：写的脚本按 `\r\n` 切行，而仓库里**行尾是混的** ——
`upgrade.py` / `make_icon.py` / `test_maint.py` 是 LF，其余是 CRLF。
按 CRLF 切 LF 文件会得到「整个文件一行」，索引直接越界。改用
`readlines()`（每行自带原行尾）才对，改完逐个验过行尾没变。

**2. `upgrade._pip()` 的超时改成独立 watch 线程（观察 B）**

原来写的是「读到一行之后判断一次 `time.time() - t0`」，而 `readline()`
是阻塞的：pip 卡住不吐东西时（网络断了最常见）代码停在那一行，**超时
判断一次都执行不到**，1800 秒的上限形同虚设。

这个坑 `models.download` 和 `torchdep.install` 都踩过并修好了，
`torchdep` 那边的注释写得很清楚 —— 这条链是漏的。

实测证明过测试有效：用旧逻辑跑同一个「卡死的假进程」，timeout 设 0.5 秒
**实际跑满 10 秒、进程没被杀**；新测试的两条断言都会红。

**3. `upgrade.install()` 检查备份结果（观察 C）**

调 `backup()` 之后不看 `ok` 就往下装。整套事务设计都建立在「装之前先
备份」上，而回滚是「照着备份目录里有什么就恢复什么」—— 备份空的话回滚
什么也做不了，那时环境已经被 pip 动过了。

备份失败概率确实很低（硬链接同盘必成、`_site_dir` 有 sysconfig 兜底），
但这一步失手的代价是环境废掉。拦住时状态仍是 `downloaded`，用户下次
还能重试安装，不丢东西。

**4. `probe.scan_dir()` 加深度护栏 `MAX_SCAN_DEPTH = 12`（观察 D）**

用户可能把 `C:\` 拖进来，那会让 `os.walk` 跑遍全盘再逐份
`pymupdf.open` 取文字，界面假死几分钟。

🔴 **只加深度、不加数量上限**：数量上限会造成静默截断（用户不知道有
文件被漏掉），违反这个项目「绝不假装」的原则。12 层是「正常用法永远
碰不到」的量 —— 按学科/年级/章节建最多三四层，留了四倍余量。
`models._find_snapshot` 出于同样理由早就有 `max_depth=6`。

**5. `main.js` 的 `open-file` 只放行 `.docx`（观察 E）**

`shell.openPath` 是「用默认程序打开」，对 `.exe` 就是执行它。页面 HTML
是字符串拼出来的，万一哪天有个转义漏洞，「能打开任意文件」立刻升级成
「能执行任意程序」。隔壁 `open-url` 早就卡了域名白名单，这条危害更大
反而什么都没卡。

限制成 `.docx` 不损失任何功能：渲染层只在两处用它，传的都是转换产物 ——
正品 `r.docx` 和判失败改名的次品 `r.degraded`（`xxx【公式未完全转换】.docx`，
改的是文件名，扩展名没变，已验证）。

**6. `check_package.py` 加 package.json 版本号检查**

`build_release.py --version` 会更新 `version.json` 和 `使用说明.txt`，
唯独不碰 `app/package.json`，所以每发一版它就更落后一版。注意两边格式
不一样：`version.json` 是 `v0.2.1`，package.json 不带 `v`。

### 查过之后认为不该改的

| | 为什么 |
|---|---|
| **观察 A** `vcredist` 不验签名 | 有合理理由：更新包走**第三方镜像**（ghfast/gh-proxy）所以必须强校验 sha256，而 vc_redist 是直连微软、不走镜像，靠 TLS 是成立的。加 `Get-AuthenticodeSignature` 是可选加固，不是缺陷 |
| **观察 F** XML 未显式关实体 | 实际不可利用：`mml` 来自 KaTeX 结构化生成的输出（不会产 DOCTYPE），XSL 来自本地 Office 安装目录 |
| **模型误删后的恢复入口** | 小蔡定的。启动自检会自动把人引到下载屏（`app.js` 的 `DOMContentLoaded` 里判 `!d.models.ok` 就跳 `page='model'`），而且底层是增量下载，缺什么补什么，不用重下 4.6 GB。**缺口是真实的**：「重新检查」按钮只在阻塞屏有，环境检测页的「更新模型」条件里第一项就是 `mu.ready`，所以模型缺失时那个按钮不出现 —— 用户在软件开着的时候删了模型，界面上找不到重下入口，得重启。小蔡判断「一般人都会想到重启」，收益不抵改动 |

### 一件没能查清的事（**2026-09-07 查清了 → 见第二十二节**）

改动过程中跑全量测试，出现过**一次** `FAILED (errors=1)`，随后连跑四次
都是 `OK`，没能复现，也就没抓到是哪条。

线索：`test_upgrade.py` 里有大量 `io.open(...).write(...)` 不关闭（跑测试
时满屏 `ResourceWarning: unclosed file`），而 Windows 上未关闭的句柄会让
后续 `shutil.rmtree` 偶发失败。

这条影响的是 RELEASE.md 第一节「红一条都不许发」这个判据的可信度 ——
一个会偶发变红的套件，等于给发版门禁装了个不稳的哨兵。**没修，因为
没复现出来，改法只能靠猜。** 下次再遇到要立刻把完整输出留下来。

## 十一、v0.2.2：小蔡真机升级时报的两个问题（2026-09-05）

小蔡从 v0.1.1 升到 v0.2.1 之后立刻报了两条。两条都是真的，而且**都跟
第九章那轮改动有关** —— 一条是我改漏了，一条是我改出来的。

### 问题一：点了更新，半天不出进度条

点更新之后要走三步才出进度条：

| | v0.1.1 | v0.2.1 | |
|---|---|---|---|
| ① 重查 GitHub 拿地址和校验值 | 串行，直连不通一条条等 6 秒 | **1.01 秒**（实测，并发赛跑） | 第九章改的 |

（① 这一格的做法在同一天又改了一次 —— 见本章末节，现在是「六条一起等、
总预算 3 秒」，实测 1.13~1.93 秒。这里保留当时的数字，因为下面两个问题
是在那个版本上发现的。）
| ② 挑下载源 | 小包不测速，按名单顺序 | 同左 | — |
| ③ 连第一条线路开始下 | 串行，`urlopen(timeout=30)` | **一模一样** | **漏了** |

根因在第 ③ 步：挑源是串行的，`_fetch_one` 的连接超时 30 秒，六条最坏
**180 秒**。而下载走的是 `objects.githubusercontent.com`，跟 API 不是
一条链路 —— **API 能通不代表下载能通**，所以 check 很快也照样卡在这里。

跟 `check()` 原来的毛病是同一个形状。第九章只修了查版本那条，下载这条漏了。

### 顺带查出来一件更要紧的：「自动（最快的）」是假的

小蔡问「自动真的是实时用最快的吗」，查下来**两层都不是**：

1. 更新包 0.5MB 低于 `PROBE_WORTH_BYTES`，`probe_mirrors` 直接返回
   `bps` 全 0，排序后就是名单原顺序 —— 每次都落到第一条
2. **就算用户手动点了「测下载速度」，那个结果也不会被下载用上。**
   `probeUpdSpeed` 测完只做一件事：`st.upd.lines = d.lines`（更新显示）。
   而下载传的是 `st.updPick`（用户手动点选的那条），没点就是空串

所以测速纯粹是「给人看的数字」，对实际下载**零影响**。而界面上写着
「自动（用最快的）」、title 写着「每次都挑最快的那条」—— 承诺了一个
不存在的行为，正好违反这个项目的头号原则。

### 问题二：线路从「4 条可用」变成「1 条可用」

**这条是第九章改出来的。** `api_race` 改成并发赛跑之后，第一条成功就
`break`，剩下五条没跑完，后端标 `pending`。而前端 `pages.js` 只数
`ok===true`，把没测的算成了不通。

我当时在 `update.py` 的注释里写着「界面上显示『检测中』」—— 而
`pages.js` 和 `actions.js` **各 0 处引用 `pending`**。典型的
「后端加了字段、前端没接」，跟第九章自己抓到的 `note_run` 字段名对不上
是同一类错，隔了一轮我自己又犯一次。

网络其实没变差，反而查得更快了（省掉 5 秒），是显示在骗人。

⚠️ **下面这几条只把显示改对了，没改「真的只测了一条」这件事。** 当天
稍后又翻了一轮，`break` 本身被撤掉了 —— 见本章末节。所以本节说的
「第一条成功就 `break`」描述的是当时的代码，不是现在的。

### 改了什么

1. **前端认 `pending`**：折叠行显示「N 条已通过，M 条未测」而不是
   「N/6 条可用」；展开表里 pending 那几条写「未测」而不是「连不上」
2. **测速结果自动生效**：`probeUpdSpeed` 拿到结果后把最快的填进
   `st.updPick`，用户仍可手动改回「自动」或别条
3. **点更新时若没手动选线路，先并发测一次速再下**。测速本身就是并发
   探测，一两秒同时探明哪条通哪条不通，把「等第一条超时 30 秒」整个绕开
4. **挑线路那几秒不再是黑盒**：主区显示「正在挑最快的线路…」。用独立的
   `st.updPickingForDl`，不复用 `updProbing`（那个是手动测速态，只让线路
   表里的按钮变字，会把主区盖掉）
5. 文案对齐：「自动（用最快的）」现在名副其实，title 补上「要一两秒」

前端测试 135 → 138 条，三条新的分别钉住：pending 不算不可用、展开表写
「未测」、挑线路时界面要说话。

### 收尾：查版本绕回 v0.1.1 的做法（同日第三轮）

上面「前端认 `pending`」只是把显示改对了 —— 界面不再撒谎，但**六条里
真的只测了一条**这件事没变。小蔡跟着问了一句「之前 0.1.1 为什么可以迅速
显示正确的线路」，翻 v0.1.1 的代码才发现，原来那版就是对的：

```python
for i, (m, d, e, ms) in enumerate(ex.map(one, API_MIRRORS)):
```

`ex.map` 并发发六条、遍历完六个结果。**并发的关键性质是「等全部 = 等最慢
那条」，不是六条时间相加** —— 所以它 1.1 秒就能给出六条完整明细，又快又全。
它唯一的毛病是直连被墙时要陪那条卡满 6 秒超时。

第九章为了治那 6 秒，改成「第一个成功就 `break`」。结果是**治好了边缘情况，
把常规情况（直连能通）的明细砍成一条** —— 拿六条真实状态换 0.2 秒，赔死。

中间还错过一版：**「第一个成功之后再宽限 N 秒」**。基准点错了 —— 第一条
本来就慢的话，从它成功开始再等 N 秒，总时长照样失控。上限必须从**发出
请求那一刻**算起，不是从某个中间事件算起。

最后的做法（`update.API_DETAIL_BUDGET = 3.0`）：六条一起发，从发出那一刻
起总共给 3 秒。正常网络 1.1 秒全回来，`while` 循环自然结束，根本用不到这个
上限；直连真卡死也最多 3 秒返回，那条标 `pending`（未测），**不写成
「连不上」** —— 没验证过的结论不许报。

实测四次：1.13 / 1.15 / 1.18 / 1.93 秒，每次都是 通 5 / 未测 0 / 挂 1。

Python 测试 407 → 408 条。另有两条改了钉的东西：

- `test_有一条秒回也要等其余线路` —— 原来钉的是「break 之后其余标 pending」，
  那是**在为错误行为兜底**，现在钉相反的事
- `test_第一条慢且失败时不等它` —— 场景原来用 0.6 秒，比预算还短，两种行为
  下结果一样、区分不出来；改成明显慢过预算，并断言那条标 `pending`

**这一轮的教训**：一个「优化」如果只在边缘情况下赚、在常规情况下赔，那它
多半是负的 —— 因为常规情况才是天天发生的。改之前先问「这条路平时走的是
哪个分支」。

### 一个中途改掉的判断

原本还打算把测速时间从 2 秒降到 1 秒。动手时想清楚了：**2 秒是为了排序
准，而它对比的是 30 秒超时** —— 省那 1 秒毫无意义，反倒可能因为采样太短
选到慢线路。这条没做。

### 留下的账（**2026-09-06 定「不做」，而且这条本身写错了 → 见第十八节**）

`/api/update/probe` 内部自己调了一次 `update.check()`（约 1 秒），而随后
`/api/update/download` 的 `_upd_work` 又调一次。点一次更新查两遍版本，
多花 1 秒。要省得改后端接口（让 probe 把 asset 一并返回给下载复用），
收益 1 秒、改动落在更新链路上，**这次没做**。

## 十三、剩余时间估不准，想按真实速率自适应（2026-09-06 小蔡提，**方案已定 → 见第十七节**）

跟上一条同一次会话提的：**每次的倒计时非常不准**。小蔡的想法是「根据每个
用户每台机器的真实转换速率，不断自我调整总时间」。调研完他定「先不做」，
结论留在这儿。

### 先说清楚：自适应**已经有一半了**，别当没有

`_remain()`（`server/main.py:915`）里已经在用真实速率：

    real_e = t.get('real_elapsed') or 0
    real_p = t.get('real_pages') or 0
    if real_p and real_e:
        spp = real_e / float(real_p)      # 已转完那几份的真实速度

而且那段注释记着一个踩过的坑：速率只能用 `done_elapsed`（最后一份转完那刻
的耗时）算，**绝不能用 `elapsed`** —— 写成 `elapsed / done_pages` 会导致
「转得越久 → 说要等得越久」，实测从 520 秒一路涨到 1400 秒。改的时候别把
这个坑再踩回去。

### 那到底差在哪：两个缺口

**缺口一（小蔡的想法正好补这个）：跨会话不记忆。**
`real_elapsed / real_pages` 是**每个任务**从零开始的。关掉软件、或者新起一批，
第一份永远退回出厂值 `SEC_PER_PAGE_GPU = 26.0`（`server/main.py:688`）。
按机器把真实速率存下来，下次第一份就不用吃那个出厂值。

**缺口二（其实更痛，小蔡最常见的用法就撞这个）：单份文件内部完全没有自适应。**
拖**一份**大讲义进去时 `done=0`、`real_p=0`，**全程**用 26 秒/页。
干净环境下 56 页 x 26 = 24 分钟估值 vs 实际 1814 秒（30 分 14 秒），偏低约
25% —— 不算离谱。但只要机器上有别的东西抢 GPU，实际能翻一倍以上（那次
1 小时都没跑完），而界面上那个数**从头到尾一动不动**。
批内自适应对「只转一份」这个最常见的用法**等于不存在**。

### 🔴 主因是「有没有东西在抢 GPU」（2026-09-06 更正，原结论写反了）

**这一节的第一版是错的，留着当教训。** 原话是「主因未必是机器，可能是文件
复杂度」，依据是出厂值 26 秒/页 vs 实测 66 秒/页、同机同卡差 2.5 倍。

那个 66 秒/页的样本**是脏的** —— 小蔡后来说「上次是两个软件一起工作」。
同一份 56 页 ok.pdf 在干净环境下重跑：**1814 秒（30 分 14 秒），32.4 秒/页，
613 个公式转成 612 个**（`logs/last_run.json`，2026-09-06 10:30:42）。

修正后的事实：

| | 秒/页 | 出处 |
|---|---|---|
| 出厂值 `SEC_PER_PAGE_GPU` | 26.0 | 2026-08-31，262 秒 / 10 页 |
| 干净环境实测 | **32.4** | 2026-09-06，1814 秒 / 56 页 |
| 有别的软件抢 GPU 时 | **> 64** | 同一份文件，1 小时都没跑完 |

**出厂值其实相当准**（偏低约 25%），「死数差好几倍」这个前提不成立。

**这对方案设计的影响是反过来的：**真正的波动来自**同一台机器在不同时刻的
负载**（你开着别的软件没），而不是机器之间、也不是文件之间的差异。所以：

- 「按机器存一个速率」（小蔡原想法）**价值比原先估计的低** —— 同一台机器上，
  开不开别的软件就能差一倍，存一个数覆盖不了
- **实时自适应（下面的方案 2）价值反而更高** —— 只有「这一份文件此时此刻
  跑出来的速度」能同时反映负载和内容

🔴 **一个样本推不出确定性结论。** 第一版就是栽在这儿：手里只有一次运行
记录，却下了「约 54 页是红线、确定性的不是偶发」这种强断言，被一句
「上次是两个软件一起工作」直接推翻。

真要做准，方向大概是这几个里挑，**得先跟小蔡定**：

1. **按机器存速率**（小蔡原想法）—— 最简单，补掉缺口一，不解决文件差异
2. **单份内部按 MinerU 的页面级进度实时推**（`Predict: x/56`）—— 补掉缺口二，
   而且天然把文件复杂度算进去了：这份文件自己跑出来的速度最准。代价是要
   解析阶段进度并区分「页面级」和「公式级」两轮，`extract.parse_progress()`
   已经能认出阶段名和 x/y，地基是有的
3. **两个都做**：先用机器历史速率给个开局值，跑起来后立刻换成这份文件自己的实测

倾向 3，但 2 是里面最关键的一步 —— 它同时解决「开局不准」之外的所有不准。

### 还要注意

- 缓存命中的那些份**不能拿来算速率**（现有代码已经防了：`real_pages` 只统计
  真跑过 GPU 的，全缓存命中时退回出厂值）。加机器级记忆时同样要防，
  否则会把「2 秒转完一份」写进历史速率，之后估值全线崩坏
- 显卡不达标现在是**当场失败**，所以不需要再留 CPU 的速率估值
  （`SEC_PER_PAGE_GPU` 上面那段注释解释了为什么把 CPU 那个数删了）

讨论完的结论是**这几条不能同时满足**，方案因此没定，先记在这儿。

#### 一份 PDF 转 Word 的三个大环节（实测耗时）

用缓存命中的方式单独量了 ① 和 ③（`ok.pdf` 有桶，② 会秒回）：

| | 环节 | 56 页那份的耗时 | 占比 |
|---|---|---|---|
| ① | 体检 `probe.probe_pdf` | **0.07 秒** | — |
| ② | 提取 `extract.run`（GPU / MinerU） | **1814 秒** | **99.8%** |
| ③ | 出 Word `todocx.md_to_docx`（612/613 公式走 XSL、18 表、132 图） | **3.19 秒** | 0.2% |

**`convert.py` 里「探测和出 Word 两步是瞬时的，不发假进度」这句实测成立** ——
③ 只要 3 秒，不用给它加进度。改动范围锁死在 ② 内部。

#### 现状的 bug：顶上那条算的是「阶段完成度」不是「文件完成度」

`pages.js:1145`：

    bar(t.current + (t.stage_total ? t.stage_cur / t.stage_total : 0), t.total)

`t.current` 是「第几份文件」，后面那项本意是「当前这份完成了多少」，
但喂进去的是**当前阶段**的比例。一份文件内 MinerU 跑六个阶段、每个都从 0 涨到 1，
于是这条进度条**一份文件内涨满又清零六次**。

#### 三个「做不到」，按硬度排

1. **实时性有上限，且不归我们管。** 进度源是 MinerU 自己的 tqdm，
   实测第一轮**每 4 页才吐一行**（间隔 40~75 秒）、第二轮每 45 项一行
   （30~80 秒）。查过 `mineru` 源码，**全部用 tqdm 默认参数**，没有
   `mininterval` / `miniters` 可调。所以进度条最长会有一分多钟不动。
   唯一的补救是两次真实数据之间插值外推 —— **但那是编的**，那一段真卡住时
   插值还会继续爬，反而骗人。不建议做。
2. **全局百分比必然是估算，而且不是权重准不准的问题。** 第二轮的总量
   （那 1100 个元素）**要等第二轮开始才知道**。第一轮跑着的时候没人知道后面
   还有多少工作 —— 只能猜。
3. 因此**「贯穿全程」和「完全准确」不能同时成立**。

#### 能保证的是什么

- **阶段真实存在**：名字全部来自 MinerU 的 tqdm desc，只做翻译，不造假阶段
- **阶段内的 x/y 完全准确**：MinerU 报什么就是什么
- **数据不延迟**：我们这边不缓冲，吐一行显示一行

不能保证的只有「整体完成了百分之几」这一个数。

#### 三条路（等小蔡定）

- **路一 · 完全准确，放弃全局条**：只显示当前步骤名、这一步的真实 x/y、
  已完成步骤清单、已用时间。每个数字都能追溯到 MinerU 的一行输出
- **路二 · 全局条用真实工作量而不是时间**：进度 = 已完成页数和元素数 / 总量。
  每一格对应真实做完的工作。代价是第二轮开始时分母从 56 跳到 1156
  （只能放慢不能退），而且单位不等价（一页约 14 秒、一个元素约 0.85 秒），
  条子前面爬得慢后面飞快
- **路三 · 保留全局条但明说是估算**：不标百分比数字，只画条，用来判断
  「还活着」而不是「还剩多少」

Claude 倾向 **路一 + 路三的组合**：条子照画不标数字，下面用文字给完全准确的
当前步骤和 x/y。

#### 顺带澄清一个「假难点」

本节前面写着「页数得从别处拿，这是这个方案的真正难点」。**不成立** ——
`convert.pdf_to_word` 的 ① 体检 0.07 秒就填好了 `rep['pages']`，
而进度回调 `_prog` 是它内部的闭包，直接读得到。区分两轮 Predict 不用绕路。

#### 权重（如果走路二或路三，会用到）

按更正后的实测：逐页识别约 **44%**、识别公式和文字约 **51%**、其余五个小阶段
加出 Word 约 **5%**。⚠️ **这个比例本身会随文件变** —— 第一轮正比于页数、
第二轮正比于元素数，公式密集的讲义第二轮会长得多。写死就一定不准，
要准得在干净环境跑几份不同类型的讲义量出波动范围。

界面方案的可交互演示（1:1 复刻软件配色尺寸，能播放对比现状和三个方案）：
`_scratch\20260906_progress_bar_demo.html`。⚠️ 那份里的权重还是旧的 65/30，
以本节的 44/51 为准。

**这个教训要记住：验 cubin 匹配不能用 matmul。**

### 三个现存 bug

1. **1080Ti 配新驱动会装到跑不了的通道**。sm_61 的卡按现有表命中 cu128，

### 驱动门槛：抄 light-the-torch 的表，别自己查

PyTorch wheel 自带 CUDA runtime，走 **minor version compatibility** ——
同一 major 内只要驱动够该 major 的最低值，不需要各 minor 的 GA 门槛。

**Windows（直接取自 `light-the-torch` 的 `_cb.py::_MINIMUM_DRIVER_VERSIONS`，
它标着来源是 NVIDIA release notes 的 Table 2）**：

```
CUDA 13.0 / 13.1   ->  580.0.0
CUDA 12.0 ~ 12.9   ->  528.33      同一 major 全部共用一个值，这就是 minor-compat
CUDA 11.x          ->  452.39      代码里现在写的 452 是对的
```

它的 Linux 表同理：12.x 全是 525.60.13、13.x 全是 580.65.06。
**「同一 major 共用一个门槛」在两个平台上都成立**，这比任何论证都直接。

这一格的说法**换过三次，前两次都错**：

- 代码里现在写 525 —— 那是 **Linux** 的数（525.60.13），Windows 该是 528.33
- Claude 一度说 560.76 —— 那是 CUDA 12.6 的 **GA** 门槛，wheel 走 minor-compat
  用不着那么高
- Claude 再改口说 527.41 —— 还是不对，正确是 **528.33**

顺带解开 `DESIGN.md` 里那条悬案 ——「CUDA 13.0 >= 527.41 这个数明显不对」：
527.41 本来就不是 13.0 的门槛，它是 12.x 那一档的数（且精确值是 528.33），

## 十六、`%TEMP%` 里的 pip 解包残骸（2026-09-06 发现，**同日已做**）

跟 pip 缓存那条（第四节决策台账「否掉：把 pip 缓存改到安装目录」）是同一类漏，
但性质更差：**pip 缓存留着还有复用价值，这些残骸对谁都没用。**

### 机制

pip 装一个大 wheel 时，磁盘上同时存在三份：http 缓存里一份、
`%TEMP%\pip-unpack-xxx` 解包一份、装进 site-packages 解压一份。
一个 2.5 GB 的 wheel，安装过程峰值要占 2.5 + 2.5 + 4 约等于 9 GB。

**正常跑完 pip 会自己清掉 TEMP 那份。中断就不会** —— 进程被杀、断网、
用户点取消、关机，那几 GB 就永久留下。

### 实测（本机，2026-09-06）

`%TEMP%` 里扫出 **45 个 `pip-*` 目录、合计 1709.6 MB**，其中：

- `pip-unpack-q5l1ae7j` **1640.2 MB**，2026-08-21 —— 里面是
  `torch-2.11.0+cu128-...whl`，**只有 1,719,926,784 字节，而完整的是
  2,753,189,216（62.5%）**。那次下载断了，8-31 才装成，这个半截文件从此没人管
- 07-01 那批六个共 68 MB —— 装 opencv / numpy / pillow / scipy 时留的

顺带给决策台账补一条数据：「否掉自己写断点续传下载器」那条的理由之一是
「没有数据支持『下载经常中断』这个假设，一次失败记录都没有」。
现在有一次了（8-21 断在 62.5%）。**但这条证据要打折扣** —— 它只证明断过一次、
发生在开发机而不是用户机器，也不排除是自己关窗口造成的。当时否掉的判断仍然成立。

### 为什么值得管

**用户机器上会发生一样的事。** 软件给用户装 torch 走的就是 pip，
用户装到一半断网或关机，几 GB 就留在 `C:\Users\<用户>\AppData\Local\Temp`。
而「删掉软件文件夹 = 卸载干净」这个承诺**覆盖不到 `%TEMP%`** ——
跟 README 里那句一样对不上。

pip 缓存那条已经决定「留着，万一别人用得上」（实测证明这个判断对，
缓存里确实有别的项目的包）。**但 TEMP 里的解包残骸不适用这个理由**：
它是安装过程的中间产物，装完就没用，中断留下的更是死文件。

### 建议改法（小、收益直接）

环境检测页那个「缓存扫描与清理」现在只扫 pip 缓存，**把 `%TEMP%\pip-*`
一起扫进去**，按目录列大小和日期，让用户自己决定删不删。

改动只在扫描那一处加一个目录，不碰安装流程。风险点是别误删**正在进行中**
的安装留下的目录 —— 判据可以是「最后修改时间超过 N 小时」，或者干脆只在
没有安装任务在跑的时候才显示这一栏。

### 2026-09-06 落地记录

做完了，但「建议改法」那段里**有一句是错的**，另外三件是动手之后才查出来的。

**一、「改动只在扫描那一处加一个目录」是错的。**
`scan_pip_cache()` 复用不了 —— 它只认 `.body` 文件（`maint.py:169`），
那是 pip 的 http 缓存格式；TEMP 里是解包目录，一个 `.body` 都没有。
新写了三个函数：`temp_pip_dirs()` / `scan_temp_pip()` / `_tree_size_safe()`。

**二、🔴 现有的 `rm_tree` 会顺着目录联接删到临时目录外面去。**

`%TEMP%` 跟 pip 缓存不是一类地方 —— 它是本机任何程序都能写的公共目录。
实测：在里面造一个指向别处的 junction，照 `clean()` 里那段 `rm_tree` 跑，
**外面的文件真被删了，`failed` 是空的，报告「清理成功」**。

两个想当然的地方都错了：

- `os.path.islink()` 对 Windows 的 junction 返回 **False**（不是 True）
- `os.walk` 的 `followlinks=False` 只管软链接，**对 junction 无效**

所以新写了 `_is_link()`（`os.path.isjunction()`，3.12 才有，取不到就退回
只判软链接）。删除另起一个 `rm_tree_safe()`，**故意不给 `rm_tree` 加参数**
—— 那个跑在 `logs/` 和 `_tmp/` 上，是软件自己的目录，行为一个字不动。

🔴 **`rm_tree` 那个洞还在**（`logs/` `_tmp/` 用的还是它）。没修是因为那两个
是安装目录里的自有目录，用户不往里放联接；要不要顺手加防护，等小蔡定。

**三、`/api/maint/clean` 的 busy 那道闸只拦转换，不拦安装。**

`_TASKS` 里只有转换任务，而 `_DL`（模型 / GPU 运行库 / vcredist）、
`_UPG`（依赖升级）、`_UPD`（软件自更新）各用一个全局字典，一个都不在里面。
这是**既有缺口**，跟 TEMP 无关：正在下 2.7 GB torch 时点「清理 pip 缓存」，
后端照样放行。加了 temp_pip 之后性质变严重（删的是 pip 正在解包的工作目录），
所以一起补了。前端按钮也跟着变灰，照抄旁边「更新模型」那个的形状。

**四、变异测试抓出测试自己的毛病 —— 跟第 4 条坑同一个形状。**

先写的那版 junction 测试，把两道防护全拆光**照样全绿**。原因是造完 junction
没调它的修改时间，它是「刚创建」的，被 6 小时年龄门槛顺手挡掉了 ——
那几条测试从头到尾根本没碰到链接防护。补上 `os.utime` 之后：

    只拆链接判断  → 红 1 条（残骸里面藏的联接）  顶层的被路径校验兜住
    只拆路径校验  → 全绿                          顶层的被链接判断兜住
    两道一起拆    → 红 3 条，全线失守

两道防护互为备份，单拆哪一道都有另一道接住，这是设计意图；能证明它们真被
测到的是第三轮。

### 2026-09-06 二次审查：又查出七处

小蔡让「查一百遍」，于是把上面那批改动逐条重审。**八处有问题，六处是我
自己刚写进去的，两处是既有的。** 按值钱程度排：

**一、🔴 年龄门槛看错了东西 —— 会删掉正在下载的目录。**

判据原来是目录自己的 mtime。实测：

    往目录里已有的文件追加 100 KB → 目录 mtime 一动不动
    新建一个文件                   → 目录 mtime 才更新

pip 下一个 2.7 GB 的 wheel 正是前一种形状：创建文件那一刻更新一次，
之后几十分钟都在往同一个文件里写。所以「6 小时没动过」这个判据，
对**正在下载的目录**恒成立 —— 它会被当成老残骸删掉。

改成看「目录里所有东西里最新的那个」（`_tree_stat`）。
前面那道 busy 闸只挡得住本软件自己的安装；用户在别的程序里跑 pip
（比如另一个 Python 项目装包）我们不知道，这条判据是那种场景下的唯一防线。

**二、🔴 问不出时间时的兜底方向是反的。**

`newest` 取不到时给的是 `0.0` —— 那是 1970 年，算出来「一直没动过」，
调用方拿去就删。问不出时间通常意味着目录正被占用或刚消失，两种都该躲开。
改成 `time.time()`（当成刚动过）。

**方向反了的判据比没有判据更危险：没判据是不删，反了是主动删。**

**三、`_UPD` 的状态机有六种，只判 `running` 漏了 `installing`。**
（idle / running / installing / need_confirm / done / error）

**四、前端判 `st.upd` 是死代码，删掉了 —— 前后端不对称是有意的。**

实测：`st.upd` 一有值，`pageMain` 就走「检查更新」那一屏（那个分支排在
`st.about` 前面），环境检测页根本渲染不出来，清理按钮不存在。所以前端
只判 `st.dl` 和 `st.upgDl` 两样，**后端仍然判三样** —— 直接打接口绕得过
前端。这个不对称在两边的注释里都写明了，别当成漏了给「补上」。

**五、🔴 `tests/front_check.js` 的收尾判断在文件中间 —— 15 条测试假绿。**（既有）

`if (bad) { ...; process.exit(1) }` 原来在第 1686 行，而它**后面还有三个
测试块**。那 15 条失败了退出码照样是 0，末尾那句「前端全部通过」也照常
打印。发版门禁认的就是这句话。

发现过程：新写的两条前端测试明明打印 ✗，脚本还是说「前端全部通过」。
判断已挪到文件真正的末尾。

🔴 这跟第 4 条坑（`formulas_ok` 那个）、跟「检查脚本自己也会错」是同一族：
**每加一条检查都要变异测试**，而且要确认它真的被计入了结论。

**六、删不掉的时候报的粒度不对。**

「删不掉要老实报」这条规矩本来就有，但这一支删的是**目录**，而复用的
`rm_file` 报的是**文件名** —— 三个残骸目录里的文件可能重名，用户看到
「x.whl（拒绝访问）」根本不知道哪个目录还在。补了一条目录级的说明
（`rm_file` 是 pip 缓存那支也在用的既有函数，没动它）。

实测：占住一个文件句柄再清理 —— `freed` 只算真正删掉的那 2000 字节，
没把删不掉的算进去；`failed` 两条，报的是「正被另一个程序使用」和
「拒绝访问」。**不假装成功**这条是成立的。

**七、`CleanReq` 的注释还写着旧的三个 key。**（我加了 temp_pip 没跟着改）

**八、`_is_link` 的注释把兜底范围说大了。**

原话是「取不到 `isjunction` 就靠调用方的 realpath 父目录校验兜底」。
不对：那个校验只保护**顶层**候选目录，而 `_tree_stat` / `rm_tree_safe`
在目录**内部**剪枝时也调 `_is_link`，那里没有任何兜底。两个环境实测都是
Python 3.12.10（发行版自带的和开发 .venv），`isjunction` 一定有，
所以现实中不受影响 —— 但注释不能写错。

## 十七、进度、倒计时、转换历史：一套方案（2026-09-06 小蔡口述定案）

把第十二、十三、十四条合并成一件事做 —— 它们要的是**同一份数据**。
下面每一条都是小蔡当场拍的，不是建议。

### 界面

顶上一行：左边倒计时、中间一条全局进度条、右边百分比。

倒计时三种状态：

    还没估出来   正在估算…（已用 2 分 10 秒）
    正常         还要约 18 分 30 秒
    归零还没转完 你的 GPU 真垃圾        ← pages.js:1155 已有，保留

中间一行是文件：圆点 + 文件名 + **当前步骤的真实进度**（「逐页识别 23/56 页」），
不再是兜底的「识别中」。

**点这一行往下展开七步清单**（做完打勾 / 正在做一个箭头 / 没到一个点），
再点收回，默认收着。🔴 **已转完的和正在转的能点开，还没轮到的点不开。**

转完之后：比估值快四成以上 → 「你的 GPU 真牛逼」，否则「转换完成」。
（`pages.js:1172` 已有，这次不动。全靠缓存秒回的不算数 —— 那是没跑 GPU。）

### 倒计时：开始前估一次，之后老实倒数，**中途不修正**

小蔡原话：「一开始是多少就老老实实的一点一点倒计时，不用根据真实进度调整，
不准就不准。」提前完或者超时就显示上面那两句预置文案。

**这条推翻了本文件第十三条里「实时自适应价值更高」的倾向** —— 那是 Claude 的
判断，小蔡的决定是：单次转换内不动，靠**跨次积累**把开局估值做准。

估值依据是从这台机器的历史里学的三个数：

| 学什么 | 干什么用 |
|---|---|
| 逐页识别，每页几秒 | 算第一轮 |
| 识别公式和文字，每个元素几秒 | 算第二轮 |
| 这类文件平均每页多少个元素 | 开始转之前不知道有多少元素，只能靠历史推 |

第一次用没有历史，用出厂值。**建议改成 09-06 那次实测的真数**：
每页 14.2 秒、每个元素 0.82 秒、每页 19.6 个元素
（1814 秒 / 56 页；第一轮 13:17、第二轮 15:03；613 个公式、1100 个元素）。
比现在写死的 `SEC_PER_PAGE_GPU = 26.0` 靠谱。

### 百分比：按权重算，**跟倒计时脱钩**

小蔡原话：「顶层的进度条不要和倒计时挂钩，还是用下面的权重，权重也靠算法
不断地调整，越用越准。」

做完的步骤把权重整个加上，正在做的那步按它自己的 x/y 折算。

🔴 **权重不写死，用上面那套数据现算** —— 这份文件预计第一轮多久、第二轮多久，
比例自然出来。所以**每份文件的权重都不一样**，公式密集的讲义第二轮自然占得多。
这一条正好解掉本文件第十四节末尾那个「权重写死就一定不准」的死结。

🔴 **只准涨不准退。** 一次转换从头到尾用开始时算的那份权重，中途不换
（换了会导致百分比跳变或倒退，而「进度条倒退比没有进度条还糟」）。

🔴 **转完之前最多 99%**，真的转完才跳 100%。

### 要记的数据：跟转换历史是同一份

| 记什么 | 给谁用 |
|---|---|
| 时间、文件名、源 PDF 全路径、产物 Word 全路径 | 历史查询：打开 Word、一键重转 |
| 成功失败、**完整**报错（现在被截到 200 字符） | 历史查询：查当时报了什么 |
| 页数、字数、图片数、识别出的元素数 | 算法：学这台机器的速度 |
| 七个阶段各花了多久、总耗时 | 算法：算权重 |

钩子位置已经是对的（`maint.note_run()` 每转完一份就写），毛病只是
`_write_json(LAST_RUN, ...)` 覆盖写，永远只剩最后一条。

### 三条细则（Claude 定的，小蔡审过）

1. **缓存命中的那几份不进统计。** 秒回是没跑 GPU，不是 GPU 快，混进去会把
   速度学成离谱的快。现有代码已经防了这一条（`real_pages` 只统计真跑过
   GPU 的），新算法照做。
2. **用中位数不用平均数。** 一边转一边开别的软件抢显卡的那几次会特别慢
   （实测 >64 秒/页 vs 干净环境 32.4），平均数会被拖歪，中位数不受影响。
3. **「每页多少元素」用比值不用绝对数**，不同页数的文件才能放一起统计。

## 二十、Word 里夹着 `text_image` 和图里的散字（2026-09-06 查明，**未修**）

### 现象

MinerU 会把**图片里 OCR 出来的文字**塞进一个折叠块：

    ![](images/ea9f472c....jpg)

    <details>
    <summary>text_image</summary>

    a'
    III
    b'

    </details>

图片本身在块外面，块里装的是图上那些标注字母。而 pandoc 把
`<details>` / `<summary>` 这两个标签当 raw HTML 丢掉，**标签之间的文字却
被当成普通段落留下了**。实测转出来的 Word：

    [前面一段正文。]
    [text_image]        ← 这个英文词直接印在 Word 里
    [a' III b']         ← 图里的散字又单独列了一遍
    [后面一段正文。]

🔴 **两种 pandoc 参数都试了**：默认的 `-f markdown`，以及代码里真正在用的
`markdown+tex_math_dollars+raw_html`（`todocx.py` 的 `_build_docx`），
**结果完全一样**。所以不是参数没配对。

**跟 HTML 表格的行为不一样**：表格是整块结构，pandoc 当 RawBlock 整块丢；
这个是「壳丢了、瓤留下」。

### 数据：11 份讲义的实测分布

`_scratch\chk.py`（2026-09-06 00:53 那次会话写的，结论当时没落盘）扫实验
文件夹里 11 份讲义的产物：

    总 details 块        1053 个
    块内含图片的         0 个
    嵌套的               0 个
    格式不匹配的文件     0 个

    summary 共 10 种：
      text_image 670   line 253   natural_image 50   flowchart 36
      area 16   scatter 12   chemical 7   contour 6   wireframe 2   bar 1

**三条结论，直接把改法定死：**

1. **不止 `text_image` 一种。** MinerU 按图的内容分十类打标记，每一类都会
   往 Word 里塞一遍那个英文词加图里的散字。1053 处。
2. **块里一张图片都没有**（`![](...)` 命中 0）。图片在块外。所以
   **整块删掉不会丢图**。
3. **没有嵌套、格式全都规整**，一个正则能干净地全删掉。

### 改法

在 `_build_docx()` 读进 md 之后、送给 pandoc 之前，把整块删掉 ——
跟 `_html_tables_to_markdown` 同一层的预处理位置：

    DET = re.compile(r'<details>\s*\n<summary>[^<]*</summary>.*?</details>\s*', re.S)

（这个正则就是 `chk.py` 里跑过 1053 块、零失配的那个。）

🔴 **删之前先数一遍 `<details>` 和 `</details>` 的个数，对不上就一个都不删。**
样本只有 11 份讲义，别的 PDF 万一格式不同，宁可不动也别删错。

**删掉的块数记进 `rep`**，第十九节那份转换报告里可以说一句「图里的文字有
N 处没有放进正文」—— 让用户知道发生了什么，而不是悄悄丢。

### 顺带查出来的：`_html_tables_to_markdown` 是死代码

`todocx.py:143` 定义了它，**全项目零调用点**（`*.py` 全文搜索确认）。
它的注释写着「不转的话 pandoc 会把 HTML 表格当原样保留的 HTML，而 docx
不支持 raw HTML，整块丢弃 —— 实测 w:tbl = 0，两张表全没了」。

而实际转换是能出表格的（v0.2.6 那次 18 个表）。所以要么表格走了别的路，
要么这个函数是某次重构留下的孤儿。**没查清，也没动它** —— 属于「先前就存在
的死代码」。真要动 `todocx` 的预处理时顺手查一下。

### 🔴 三、环境检测页滚动会跳 —— 查清了：漏了第三个滚动容器

现象（小蔡确认过）：**展开缓存明细后往下滑，跳回最顶上；有规律地跳，
一滑就跳；只在「更新组件」进行时出现。**

已经查明的：

- 重绘源是 `pollUpgrade` —— 升级期间**每秒 `render()` 一次**，对上了
  「只在更新组件时」
- `render()` 是 `innerHTML` 整体赋值，滚动容器被换掉
- **但代码里已经有保存/恢复 `.main` 滚动位置的逻辑，逻辑本身没写错**
- 环境检测页确实走 `shell`，`.main` 存在；`.fill` 没有自己的 overflow，
  滚动确实发生在 `.main` 上

**根因**：缓存明细展开后，它自己是一个独立的滚动框 ——

    <div id="cachelist" style="max-height:96px;overflow:auto">…明细表…</div>

用户滑的是**这个框**，不是外面的 `.main`。而 `render()` 当时只保存/恢复
`.main` 和 `#dllog` 两个容器，**这一处根本没人管**：写那两段的时候这个框还
不存在，后来加明细的人没想起来还有第三个。升级期间 `pollUpgrade` 每秒
`render()` 一次，于是一秒归零一次。

四个现象全对上：

| 现象 | 为什么 |
|---|---|
| 跳到最顶上 | 框是新建的，scrollTop 从 0 开始 —— 不是恢复得不准，是**根本没恢复** |
| 一滑就跳 | 升级期间每秒重绘一次 |
| 只在更新组件时 | 只有那时才每秒重绘 |
| 只有展开才看得到 | 收起来这个框根本不存在 |

**第一版修法**（当天先按小蔡说的「按最小的来」）：给框一个
`id="cachelist"`，`render()` 里跟另外两个并排保存/恢复。

**当天就返工了。** 小蔡随后让按 karpathy 那套复查「有没有遗漏、有没有动到
现有代码」，一查：页面上有 **7 个** `overflow:auto` 容器，`render()` 只按
写死的选择器管了 **3 个**。没管的四处里 ——

| 位置 | 是什么 | 会犯病吗 |
|---|---|---|
| `pages.js:182` | **历史屏的记录列表** | **会** —— 而且是**修完当天自己刚造的** |
| `pages.js:957` | 升级变更清单（展开时） | **会** —— 跟缓存明细**同一屏同一场景**，隔一百行 |
| `pages.js:806` | 更新说明（完整说明展开） | 会 —— 下载更新时一边下一边翻 |
| `pages.js:633` | 下载源列表 | 不会 —— 一次性加载，没有轮询 |

刚修完「明细一滑就跳」，转头在新做的历史屏里造了个一模一样的 —— **这说明
「一个容器写一段」这个形状本身就是漏的源头**。

**最终修法**（小蔡定的通用方案）：容器上打 `data-keep-scroll="名字"`，
`render()` 一个循环按名字保存/恢复。**日志区不并进来** —— 它要的是
「贴底就跟着滚」而不是「留在原处」，保持自己那段特殊逻辑。

代码反而更少（比一个容器写一段短），而且以后新加滚动区只要顺手带上标记，
不用记得回来改 `render()`。

配套测试按标记逐个盯（cachelist / history / upgchanges / updnotes 各一条），
四条变异全抓得住：不按名字配对、保存时全塞进同一个键、整个恢复循环拿掉、
把日志区也并进通用那套。

🔴 **这一轮写出了三条假绿测试，全靠变异抓出来**：
  · 时序那条把断言写成 `!r.port || r.port === 1234 ? false : true`，
    括号优先级让它永远不抛
  · 失败行那条只验页面上有没有文件名，而文件名在行首那列本来就显示着
  · 滚动这四条**拿着重绘前的旧元素对象断言** —— 重绘会把容器换成新元素，
    旧对象的 scrollTop 永远是刚才自己设的值，跟恢复逻辑跑没跑毫无关系
  **写完测试必须变异一次**，看着绿不算数。

### 🔴 砍掉「一键重转」

### 🔴 小蔡的一个误解，得写清楚

### 🔴 还查出三个会让用户白等的坑

**一、torchvision 不跟着升，装上去环境是坏的**

`constraints_for()` 把没勾的包钉死在当前版本（那是「只升 A 不动 B」的有意
设计）。但 **torchvision 是编译期绑死 torch 版本的** —— 只勾 torch 的话，
下好的 2.5 GB 里根本没有 torchvision，就算装上 torch 2.14，
torchvision 0.26（配 torch 2.11 的）多半加载不了。

修：后端 `pair_up()` 强制配对，有 torch 就带 torchvision，反之亦然；
mineru 不受影响。放后端不放前端 —— 不管界面怎么勾、将来谁调，
出来的组合都自洽。

**二、点一下「清理转换临时文件」，下好的 2.5 GB 就没了**

`CACHE = paths.TMP/upgrade_cache`，而清理那一栏界面上只写着
**「转换临时文件」**。用户点一下，包全没了，状态文件在 logs/ 下毫发无损、
仍写着「已下好」，于是重启后装不上还得重下。

修：清理面单独列一行「下好的升级包（等重启安装）」，`clean(['tmp'])`
绕开它，只有明确勾了才删。

**三、`pending()` 只信状态文件，不看硬盘**

承上，包被清掉之后它还会说「能装」，然后 pip 带着 `--no-index` 找不到
wheel，装失败、回滚一次，用户白等且看不懂。

修：`missing_wheels()` 真去 CACHE 里数 wheel，缺了就返回 `redownload`
并说出缺哪个。包名按 pip 的规矩规范化（小写、`-_.` 都当 `_`），
大小写不同也认得出。

### 界面（小蔡定的样子）

**不弹窗，就在升级区原地替换那两个按钮，而且不要「稍后重启」** ——
想稍后就直接不点，关掉软件下次开还在。

|---|---|

    14:52    upgrade_state.json     **根本不存在**

## 二十八、pip 残骸的判据：从「多久没动过」换成「还有没有人在用」（2026-09-07）

小蔡问「时间能不能改成别的判据」。能，而且准得多。

### 老判据两头都不准

`TEMP_PIP_MIN_AGE_H = 6` 是拿时间猜「还有没有人在用」：

- 下载超过 6 小时的大包（torch 2.5 GB 走慢线路完全可能）会被误删
- **刚产生的一个都看不见** —— 小蔡机器上 92 个残骸、519.7 MB，
  界面显示 0，因为都是刚关软件时留下的

### 🔴 一度以为可以换成「能不能改名」，实测证明当不了主判据

**Windows 上被占用的目录改不了名**，造场景实测五种情况全对（没人用能
改名；文件被打开、正在写、被当工作目录，三种都改不了）。看着很准，
于是差点就把它当主判据了。

**小蔡追问「你确定会跳过？」，一验就塌了。** 真跑一次 pip download，
在它运行期间探测新建的临时目录：

    pip-build-tracker-…   探测 29 次，29 次都说「没人用、可以删」
    pip-download-…        探测 29 次，29 次都说「可以删」
    pip-unpack-…          探测 22 次，22 次都说「可以删」
    pip-metadata-…        探测 18 次，18 次都说「可以删」
    pip-unpack-…          探测 18 次， 0 次说可以删   ← 只有这个挡住了

**5 个里 4 个在 pip 正用着的时候被判成「可以删」。** 因为 pip 大部分
时间只是「目录建着」，文件写完就关，目录本身没被任何进程打开 ——
**「能改名」只等于「此刻没有文件被打开」，不等于「没人在用」**。

我之前那句「比时间准得多」是说过头了。

### 真正在防误删的是年龄底线

同一次实测里，那 5 个目录**一个都没进清理清单**（48 次探测全程 0 个）
—— 挡住它们的是扫描那一步的年龄底线：它们刚建，最新文件时间就是此刻。

所以分工是：

| 环节 | 判据 | 挡什么 |
|---|---|---|
| 扫描 `temp_pip_dirs` | 年龄 ≥ **30 分钟** | **挡「正在用的」，这是主防线** |
| 删除 `clean` | `can_take()` | 挡「删到一半留下残缺目录」，见下 |

底线从一度改的 1 分钟拉到 **30 分钟**（小蔡定「保险一点」），给
「pip 卡住不动」买安全余量：真卡了半小时，那次下载多半也废了。扫描保持纯只读 ——
改名要写文件系统，万一中途崩了目录会留在 `.trylock` 上，前缀对不上、
下次反而永远扫不到。

### 🔴 can_take 真正的价值：不留残缺目录

第一版测试「有人用的删不掉」**直接就过了**（没红）—— 因为 Windows 本来
就删不掉被打开的文件，目录自然留下、`failed` 也报了。

但那不等于没问题：不先判断的话，删是**一个文件一个文件试**，被打开的那个
删不掉，而**同目录里没被打开的其它文件已经删掉了** —— 留下一个残缺目录。
pip 正用着它，缺了文件那次安装多半直接失败，而用户只看到「清理完成」。

写了一条能区分的测试（同目录放两个文件，只打开其中一个，断言另一个必须
还在），**红了**，才证明这个判据有价值。

### 🔴 一条老测试的假设本来就不成立

`test_刚动过的不碰` 用「**1 小时前动过**」来模拟「正在解包」。正在解包的
目录，里面最新文件的时间应该是**几秒前**；一小时一动不动的，pip 早就不在
了。配 6 小时门槛时看不出问题，门槛降到 1 分钟就露馅了 —— 它挡的其实是
「一小时前的老残骸」，不是「正在进行的下载」。改成按真实形状造。

### 效果（小蔡机器实测）

    软件看得见的        : 92 个，519.7 MB   （改之前：0 个，0.0 MB）
    扫描耗时            : 0.07 秒

界面那一行的说明也跟着判据改了：「92 个目录，正在用的会跳过」。

四条变异全抓得住：删之前不问占用、can_take 永远说没人用、试探完不还名字、

    删备份的函数                  ❌ 根本没写

**又一个「做好了没人调」** —— 这已经是这两天第五个了（下好不装、下完不
刷新、状态没落盘、历史没出口，加这个）。

补齐：

- `upgrade.prune_backups(keep=1)` —— **默认留最新一份**。多留 4 GB，
  换一次「装完发现不对还能退回去」的机会，划算。想全清传 `keep=0`。
- 清理面加一行「升级备份（装成功后就没用了）」，走现成的 `list_backups()`
- `clean(keys=['upgrade_backup'])` 接上，**没勾就一份都不删**

🔴 **`phase=installing` 时一份都不删**：那意味着上次装到一半断了，下次开机
要靠备份回滚 —— 这时候删备份等于把回头路砍了。返回 `why` 说明原因，
由清理面显示给用户。

### 顺带：`git checkout` 会改行尾

撤回两个测试文件的改动时用了 `git checkout`，git 的 `core.autocrlf` 把它们
从 LF 转成了 CRLF，跟仓库里存的不一致。功能没影响（Python 两种都能跑），
但下次提交时 diff 会显示**整个文件全变了**，真正的改动被淹没。已还原。

**教训：`git checkout` 撤回改动之后，顺手核一下行尾。**
