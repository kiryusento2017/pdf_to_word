# PDF 转 Word · 设计

一句话：把 PDF 讲义转成 Word，**文字、公式、表格、图片都是原生对象**，不是截图。

终末诗篇工作台（`edu_book_generator`）的专精版——那边是「PDF → 题库 → 重新组卷」，
这边只做「PDF → Word」这一段，不入库、不判题、不组卷。

---

## 一、用户装了之后会做什么

```
【首次启动 · 只出现一次】
1. 双击 `PDF转Word.exe` → 打开（620x440 的小窗口）
2. 自检：显卡 / 转换引擎 / 公式引擎 / Office / **GPU 运行库** ——
   结果压进状态栏，不占屏
3. 缺 GPU 运行库 → 拦主区，给「现在就装」（约 2.8 GB，见第七节）
4. 模型没有 → 并发测速各源 → 显示「预计几分钟」→ 最快的默认选中
   （**只是记下源，不在这一步真下载** —— 见第八节）
5. 就绪

【日常】
5. 拖入 PDF（单文件 / 多文件 / 整个文件夹）
6. 表里显示：文件名、页数、**哪几页没有文字层**
7. 点开始转换
8. **同一张表原地变进度**：顶部换成「还要约 X 分 Y 秒」加总进度条，
   每行显示自己的状态（完成 / 正在转 + 阶段 / 排队）。
   状态栏有「日志」按钮，点开覆盖主区看 MinerU 的实时输出
9. 转完的行就地长出「打开 / 文件夹」链接
```

界面形态（2026-08-31 定）：**单主屏 + 状态栏**，参照 Geek Uninstaller
那一类的小工具。主体永远是那张文件表，不跳屏 —— 用户的视线不用在几屏
之间重新找位置。三段结构（工具条 / 主区 / 状态栏）里主区是 `flex:1`，
所以任何状态下都铺满窗口，包括空态的拖放提示。

自检只在必须让用户拿主意时才拦主区，按严重度排：安装目录不可写 →
没装 Office → 转换引擎缺失 → **缺 C++ 运行库** → 缺 GPU 运行库 →
显卡不达标。C++ 运行库排在 GPU 运行库前面是 2026-09-02 改的 ——
它是那 2.8 GB 的前提，顺序反了用户就白下一趟（见第七节坑五）。
前五种硬拦，但**每一屏都给出路**（缺 C++ 运行库和缺 GPU 运行库那两屏
都有「现在就装」，缺 Office 那屏有「去微软官网」）；显卡不达标是软拦，
给「仍然继续」和「退出」，**不替用户做主**。

任何下载都不给黑盒：进度条（真实字节数）+ **跑的那条完整命令** +
滚动日志，失败了日志留在原地不跳走。2026-09-02 真机上就是靠这个才
定位到「torch 的 c10.dll 加载不了」—— 那跟网络和下载源毫无关系，
而当时界面把它显示成了「测速失败」。

第 8 步为什么是剩余时间而不是百分比：MinerU 的阶段进度是真的，但各阶段耗时
差 100 倍（实测同一次转换：「分析版面」16 秒跑完、两个「识别中」合占 91%、
「处理页面」跑满一整条只要 1 秒）。「分析版面 10/10」看着快好了其实才走 6%。
用户只关心还要多久，而页数 × 实测速率能答这个问题。

**阶段内的 x/y 数字不显示**（2026-09-02 改）。两次真机反馈指向同一件事：

  · 「准备版面一直是 0 然后突然跳到识别 2/11」—— 有些阶段不吐中间值
  · 「刚刚文件本来是 5/11，现在是 5/247，我无语了」—— 换阶段时总数
    换了单位（页 → 检测到的文本块）

数字本身没算错，是它压根不该给用户看。现在只留阶段名和一条比例条：
能看出在动就够了，「还要多久」在顶上单独显示。

原设计还有第 10、11 步（转换报告：标出哪几处公式可疑、哪几页走了 OCR，
用户只核对被标出来的地方）—— **没做**，挪到第八节。

第 6 步只报事实，**不下「好 / 差」的结论**（理由见下一节：初版在这里栽过）。
「第 27、28、30 页没有文字层」是客观的，那几页整页当图识别、出错概率更高，
值得单独看一眼；而「这份不会出错」是我们给不出的承诺，给了就是骗人。

## 二、文字准确度的真相（2026-08-31 实测推翻了初版设计）

初版这一节写着「PDF 有文字层 → 走 txt 模式取文字层 → 正文几乎 100% 不出错」。
**三个说法全错**，实测记录在此，免得后人再推一遍同样的错。

### 错在哪

起因是 MinerU 的产物里有个错字：「9. 己知函数」（应为「已知」）。
当时的推理是：这批 PDF 都带文字层，而配置用的是 `method=ocr`（把文字层扔掉
当图片重新识别），所以错字是 OCR 认错造成的，改走 txt 就能消掉。

**这条推理链一环都不成立**。同一份 PDF 跑三种模式：

| 模式 | 正文字符 | 行内公式 | 「己知」 | 「已知」 | 用时 |
|---|---|---|---|---|---|
| txt | 10187 | **131** | 1 | 13 | 202s |
| auto | 10187 | **131** | 1 | 13 | 178s |
| ocr | 8972 | **213** | 1 | 13 | 238s |

「己知」**三种模式都是 1 处**。直接查原 PDF 的文字层：

```
第 4 页文字层：9. 己知函数 ． （1）若 的解集为 或 ，求的…
文字层里「己知」1 次、「已知」13 次
```

**错字在原 PDF 里就是错的**，是原书排版打错的字，跟 OCR 毫无关系。
「有文字层」是真的，「OCR 是错字来源」是凭空接上去的——两件事都成立不代表
它们之间有因果。

### 实测得出的结论

**默认用 `ocr`**：文字准确度三种模式**一样**（错字都是原书的，谁也消不掉），
但 txt / auto 丢了 82 个公式（38%）——文字层里没有公式，原文那句
「5. 已知不等式 [空] 的解集为」中间就是空的，txt 模式直接放弃，
ocr 把那些图形化的公式识别成了 LaTeX。多花 40 秒换 82 个公式，值。

`auto` 也不能用：它对这份 PDF 的判定结果与 txt **一字不差**（10187 字符、
131 公式），等于走了 txt 路线。

### 所以这个软件能承诺什么

| | 能说的 |
|---|---|
| 正文文字 | **不做准确率承诺**。原书本身可能有错字，OCR 也可能认错，我们分不清也修不了 |
| 公式 | 转成 Word 原生对象（可编辑可搜索），转不了的标出来 |
| 表格 | MinerU 的结构，含合并单元格 |
| 图 | 按原书尺寸还原（MinerU 的 200 DPI） |

界面上**不给「文字版 / 扫描版」这种质量暗示**——那会让人以为标了"文字版"
就不用校对。只报客观事实：几页、哪几页没有文字层（那些页整页当图识别，
出错概率更高，值得单独看一眼）。

## 三、架构

```
Electron 外壳  →  spawn Python  →  FastAPI（本地端口）
   前端纯 JS                          ↓
                        probe / sources / extract / tomath / todocx
```

`paths.py` 集中管所有落点。小蔡定的规矩（2026-09-01）：**运行中产生的
一切都留在安装文件夹内，只有导出的 Word 例外** —— 删掉文件夹 = 卸载干净。

| | 落在哪 | 靠什么 |
|---|---|---|
| 模型 4.6 GB | `<安装目录>/models` | `MODELSCOPE_CACHE` / `HF_HOME` |
| MinerU 配置 | `<安装目录>/mineru.json` | `MINERU_TOOLS_CONFIG_JSON` |
| 临时文件 | `<安装目录>/_tmp/extract` | `paths.TMP_EXTRACT` |
| Electron 缓存 | `<安装目录>/appdata` | `app.setPath`，**必须在 app ready 之前调** |
| 日志 | `<安装目录>/logs` | `model_download.log` / `torch_install.log` / `convert.log` |
| C++ 运行库（补的） | `<安装目录>/runtime/python/msvcp140.dll` | 只在系统缺失时补，见第七节坑四 |
| Word 产物 | 用户自己选的输出目录 | 唯一的例外 |

前三个环境变量是落点的全部实现手段，由 `paths.child_env()` 一处给出 ——
散着写的话少传一次就漏一处，而漏了不会报错，只会悄悄往用户的 C 盘里塞几个 GB。

同一个函数还给第四个：`MINERU_DEVICE_MODE=cuda`，管的是另一件事
（不许悄悄用 CPU，见第七节）。

⚠️ **不碰用户的全局 `~/mineru.json`**。那是 MinerU 的全局配置，用户机器上
可能装着别的用 MinerU 的东西，改它等于动别人的家当。

代价是**这软件不能装进 `C:\Program Files`** —— 那目录普通用户不可写。
`paths.writable()` 在启动自检里拦这种情况，并告诉用户挪到别处。

### 模块

| 模块 | 职责 | 能离线单测吗 |
|---|---|---|
| `paths.py` | 所有落点集中管理、**怎么跑 MinerU**、找可执行文件 | 能，纯路径计算 |
| `probe.py` | 判 PDF 有没有文字层、几页、是否加密 | 能，纯读 |
| `gpu.py` | 显卡够不够用，话术给人看 | 能，可喂假的 nvidia-smi 输出 |
| `sources.py` | 多源并发测速、选源、断点续传 | 能，可 mock 网络 |
| `models.py` | 认已有模型、下模型、写自己那份配置 | 能，可造假的模型目录 |
| `torchdep.py` | GPU 运行库在不在、能不能真加载、怎么装 | 能，可造假的 version.py |
| `update.py` | 查 Release、多镜像测速下载、解压覆盖 | 能，可 mock API |
| `extract.py` | 调 MinerU，按页吐进度 | 进度解析能（`test_extract.py`），真跑要 GPU |
| `tomath.py` | LaTeX → OMML（KaTeX + 微软 XSL） | 能，纯函数 |
| `todocx.py` | blocks → .docx | 能，纯函数 |

**只有「真跑 MinerU」这一下需要 GPU，其余全能离线单测**——连 `extract.py` 里
最容易错的那部分（解析 tqdm 进度）也是纯函数，不用 GPU 就能测。这个切法是有出处的：
工作台那边 AI 和 GPU 混在业务逻辑里，全量测试一度从 14 秒变成 142 秒还真花钱。

## 四、公式转换：两条路

```
装了 Office → 读本机 MML2OMML.XSL → OMML
没装 Office → **拦住，引导去装**（2026-09-01 改定，见下面的决策台账）
```

⚠️ 下面那段「两条路」是**历史记录**，讲的是 09-01 之前的设计和它被推翻的
   过程。现在只有一条路。

### 实测数据（2026-08-31，解不等式那份）

Pandoc 3.11 单独跑的结果：

```
Word 原生公式 m:oMath  213 / 213 = 100%
表格 w:tbl             2（含 rowspan 合并单元格）
表格行 w:tr            12
图片 w:drawing         4 ｜ 内嵌媒体 4
残留 $...$ 源码        0
```

关键参数：**`-f html+tex_math_dollars`**。MinerU 的表格是原始 HTML，
若不让 html reader 认识美元符号包起来的是数学，它会把 `\Delta` 转义成 `\\Delta`、
`^` 转义成 `\^`，LaTeX 当场报废（实测：213 掉到 202，残留 11）。

### 决策台账

**2026-08-31**：Claude 建议砍掉 XSL 只留 Pandoc（Pandoc 已经 100%，
一条路 = 一半的测试面）。小蔡决定保留两条，故两条都实现、都测。

**2026-09-01：推翻，改成 XSL 硬性要求。** 起因是实测发现两条路的产物有
**实质差异而非风格差异** —— Pandoc 把空集 ∅(U+2205) 转成直径符号
⌀(U+2300)，那是错的；括号也不走 OMML 定界符，Word 里不会随内容伸缩。

小蔡拍板：与其让一部分人拿到次等产物还不知情，不如在门口说清楚要装 Office。
于是：

  · 没有 XSL / 没有 node → 前端拦住主区，引导去装（不让用）
  · 屋里那四条降级路径（没 XSL、没 node、数量对不上、部分公式转不了）
    **一律判失败**，不再静默产出混着两种引擎的 Word

⚠️ **Pandoc 本身不能去掉**：整个 docx 是它生成的（md→html→docx），
XSL 只是把生成物里的公式替换掉。「放弃 Pandoc」在技术上不成立。

期间讨论过让用户装 Office 的成本（Microsoft 365 ¥398/年、Office 2024
一次性 ¥898），Claude 提出这笔账不划算（前两条差异只是字符映射，
改 Pandoc 后处理半小时就能补上）。小蔡确认理解后仍坚持硬性要求，
理由是产物质量不能有两个档次。**已执行。**

**2026-09-02：把「按序对齐」换成「占位符门牌号」，并部分推翻上面那条。**

09-01 定的「四条降级路径一律判失败」里，「数量对不上」那条在真机上炸了：
pandoc 在自己的 AST 里数出 613 个公式，渲染进 docx 时却只产出 612 个 ——
一个 OCR 粘连出来的 `\\gtan`（把 `g\\tan` 认成一个命令）让它把那处退化成
纯文本。数量对不上 → 从缺口往后 70 个公式全部张冠李戴 → 只能整份判失败。
**11 份真实讲义里 1 份中招，9% 的失败率。**

根子不在 OCR，在于**替换机制依赖一个 pandoc 自己不保证的前提**：
「AST 里数出的公式数 == 渲染进 docx 的 oMath 数」。

改法：喂给 pandoc 之前就在 AST 层把每个 Math 节点换成唯一占位符
（用 `Code` 节点 —— 它在 docx 里带 VerbatimChar 样式，**必然独占一个
`<w:r>`**，省掉「占位符被拆进多个 run」这个最容易翻车的处理），
pandoc 全程只当普通文字搬运，出 docx 后按门牌号精确定位塞回 OMML。

于是三件事同时成立：

  · 不再依赖数量相等 —— 「数量对不上」这条失败路径**从此不存在**
  · 某个公式 XSL 转不了，**只影响它自己**，那一处保留 LaTeX 原文
  · 报错能说出**是第几个、内容是什么**（改造前只说「有 N 个」，等于让人猜）

**因此推翻「一律判失败」中的两条**：少数公式转不成不再废掉整份 ——
错位已经不可能发生，132 张图、18 个表、612 个转好的公式没有理由陪葬。
只有「一个都没转成」（XSL 链路整个坏了）才判整份失败。

⚠️ 这**不是**退回 Pandoc：转不成的那几处留的是 LaTeX 原文（纯文本，
一眼看得出要手改），不是 Pandoc 转的次品公式，所以不会出现 ⌀ 那类错误
符号 —— 09-01 那条决策要防的东西仍然防住了。

**判失败也不再删产物**：原来 `os.remove(out_path)`，现在改名成
`xxx【公式未完全转换】.docx` 留下。要防的是「被当成正品」，不是
「它存在」—— 转一份要四分钟，不该因为一个公式没转成就让人两手空空。
改不动名字（文件被 Word 占着）时会明确警告，不再 `except OSError: pass`
静默失守。

验证：11 份真实讲义从「成功 10 失败 1」变成「成功 11 失败 0」，
公式 2884 → 3163 全部走 XSL。

### 不做的事

微软的 `MML2OMML.XSL` **不打包进安装包**——那是随 Office 分发的版权文件，
提取出来再分发是侵权，范围大小不改变性质。读用户自己机器上那份是合法的，
本项目就是这么做。

Office 路径不写死：要扫 `Office16` / `Office15` / 32 位版 / 非 C 盘安装。

## 五、下载源：照搬工作台 B35

每类源内置多个候选；**点下载时并发对所有源各测 2-3 秒实速**；按预计耗时排序、
最快的默认选中；途中掉速自动切次优源 + 断点续传。

三条硬约束：

- **不存历史成绩**——下载是低频动作，现测成本可忽略，旧成绩反而过时误导
- **不用 ping 判优**——很多 CDN 屏蔽 ICMP，且低延迟 ≠ 高带宽
- 界面显示「预计几分钟」而不是 MB/s，**电脑盲直接点开始即可，不必做选择题**

源清单（工作台 2026-08-22 逐个实测验证，假源已剔除）：

- 模型：ModelScope／HF-Mirror／HuggingFace 官方／本地导入
- 依据：Chromium 走 npmmirror 比 Google 官方快 22 倍，torch 却是官方源更快——
  **没有哪个源是普遍最优的**，写死必然坑一批人

## 六点五、Word 用什么字体（2026-09-05）

**正文和标题都用「宋体 + Times New Roman」，同一套。**

改之前是 pandoc 内置 reference.docx 的主题字体：西文 Aptos、简体中文
等线。跟 MinerU、跟本机 Office 版本都无关 —— 换台机器打开也是 Aptos。

### 为什么是这两个

| | 理由 |
|---|---|
| **任何 Windows 都有** | `simsun.ttc` / `times.ttf` 从 Win95 就在。Cambria、Calibri 是**随 Office 装的不是系统自带** —— 本软件要求装 Office，但**收 Word 文件的学生家长不需要装**。等线是 Win10 才有 |
| **跟公式协调** | 公式是 Word 强制的 Cambria Math（衬线体），正文用宋体 + Times New Roman 同为衬线，段落里插公式不突兀；用微软雅黑那种无衬线会打架 |
| **打印清晰** | 讲义要打印，宋体本来就是为印刷设计的 |

### 为什么正文标题不分开设

**MinerU 认标题会认错**，pandoc 只能照它给的结果转。正文标题用不同
字体的话，认错的地方字体就会跳，出现「半页宋体半页黑体」的花脸。
统一之后最多是字号不对，那个不难看。标题的区分交给 Word 的 Heading
样式（字号 + 加粗）就够了。

### 实现

`todocx._set_theme_fonts()`，跟 `_add_table_borders()` 一个路数：解 zip、
改 `word/theme/theme1.xml`、塞回去。不用自定义 reference.docx —— 那要
维护一个二进制文件，没法审查没法 diff。

🔴 **中文不在 `<a:ea>` 里。** 那个标签在 pandoc 的模板里是空的
（`<a:ea typeface=""/>`），真正管简体中文的是 `<a:font script="Hans">`
那一行。只改 `<a:ea>` 的话中文字体纹丝不动。

### 改不了的

**公式仍然是 Cambria Math**，Word 强制的。正文改完之后公式里的字母
还是那个样子 —— 这不是没改干净。

## 七、显卡与 GPU 运行库（2026-09-02 改成只用 GPU）

小蔡定的方案（2026-08-31）：首次打开时强制检测，满足就继续，不满足让用户
自己选「退出」还是「硬来」——不猜、不替用户做主。

检测手段：`nvidia-smi --query-gpu=name,memory.total,compute_cap,driver_version`
一条命令拿全（本机返回 `RTX 4060 Laptop, 8188 MiB, 8.9, 572.83`）；没有 N 卡时
用 WMI 兜底查显卡名，好区分「没独显」和「有卡但驱动没装」——这两种给用户的
话术完全不同。判据：compute_cap ≥ 7.5（Turing）且显存 ≥ 6 GB。

**2026-08-31 的实测**：同一份 10 页讲义，GPU 262 秒 / 纯 CPU 460 秒 ——
慢 2.0 倍，不是十几倍。当时据此把话术从「会慢很多」（等于没说）改成了
具体分钟数，并认为「没显卡是能用的，只是得等」。

**2026-09-02 推翻了这个判断**：小蔡定规矩，这个软件**只用 GPU**。
理由不是 CPU 跑不动，是**静默降级最坑人** —— MinerU 的 `get_device()`
探不到显卡就自己换 CPU，用户完全不知道自己在等一件本可以快一倍的事。
现在 `paths.child_env()` 把 `MINERU_DEVICE_MODE` 写死成 `cuda`，
探测那一步根本不走。

配套的三条：

1. 显卡不达标**报警但不阻拦**。点了会当场报
   `RuntimeError: No CUDA GPUs are available`（实测），是立刻失败
   不是白等半小时，所以不拦是安全的。
2. 话术里不许再出现「会退回 CPU」这类退路 —— 承诺一条不存在的退路，
   比什么都不说更坏。`tests/test_gpu.py` 里有测试钉着这条。
3. CUDA 版 PyTorch 不打进安装包（4.2 GB），改成首启按需下（wheel 约
   2.8 GB），见 `pipeline/torchdep.py`。

### GPU 运行库：五个坑，都是真机撞出来的

**坑一：CUDA 版本写死。** 起初写死 cu128（最新），而它要求显卡驱动 570+
（查证自 NVIDIA CUDA DL Release Notes）。驱动低于这个数的机器，
`import torch` 直接 `OSError [WinError 1114] 动态链接库初始化例程失败`。
现在按驱动号挑：≥570 用 cu128、≥525 用 cu126、其余用 cu118。
驱动号 `nvidia-smi` 本来就一起查回来了，白放着没用。

**坑二：拿「文件在不在」当「能不能用」。** `ready()` 读 `torch/version.py`
这个文本文件，它在就报「装好了」—— 而 c10.dll 加载得起来是另一回事。
现在装完会**真起一个子进程 import 一次**再说装好了。

**坑三（最要命）：「装了但坏了」这个中间态会连累模型下载。**
modelscope 的 `logger.py:48` 这么写：

```python
if iutil.find_spec('torch') is not None:      # 只查文件在不在
    from modelscope.utils.torch_utils import ...   # 直接 import，没有 try
```

跟坑二是**同一个错误模式**。于是 torch 的三种状态里，中间那种是雷：

| torch 状态 | modelscope 的表现 |
|---|---|
| 完全没装 | `find_spec` 返回 None → 跳过 → **模型下载完全正常** |
| 装了且能用 | 正常 |
| **装了但加载不了** | 找得到 → 进去 import → **崩**，模型下载一起废 |

用户看到的是「模型下载器崩了」，跟模型、跟网络毫无关系，无从查起。
所以：**装完验不过就把 torch 卸掉**，退回「干净的没装」状态 ——
最坏也只是「模型照常下、转换时明确说缺 GPU 运行库」。

**坑四：检查排在了耗时操作后面。** 小蔡 2026-09-02：「顺序是不是不太对，
是不是应该先装 VC」。原来的流程是：

    下 2.8 GB（十几分钟）→ 装上 → 发现加载不了 → 卸掉
    → 让用户去装 C++ 运行库 → **重新下 2.8 GB**

而 `msvcp140.dll` 在不在是一次本地文件检查。把它放在失败之后当「诊断」，
等于让用户白等半小时才知道前置条件不满足。同类的还有磁盘空间 ——
下到一半空间不够，前面全白等。

通则：**任何耗时操作之前，先把能零成本查的前置条件查完。**

顺带发现：C++ 运行库根本不用让用户去装。numpy 的 Windows wheel 里自带一份
（delvewheel 会把依赖的 DLL 改名塞进 `numpy.libs/`），复制出来改回原名
放到 `python.exe` 旁边即可 —— DLL 搜索顺序里「应用程序目录」排在
`System32` 前面。零下载、不碰系统、删文件夹照样卸载干净。

但**只在系统真缺时补**。实测（2026-09-02）：

| 来源 | 版本 |
|---|---|
| numpy 自带 | 14.40.33810.0 |
| 开发机系统 | 14.50.35719.0 |

`python.exe` 旁边优先级更高，无脑复制等于把开发机这种已装机器降级到
14.40。运行库向后兼容是单向的：新版能跑旧代码，旧版跑不了新代码。
torch 若用 14.5x 工具链编译、引用了 14.40 没有的符号，这一手会把本来
正常的机器搞坏。

**坑五：「自动补运行库」这个方案根本不成立，而且判据一路判错。**

坑四那套（软件自己补一份 msvcp140）2026-09-02 当天就被真机推翻了。
小蔡装好 vc_redist 之后 GPU 库一次就过，原话是「我严重怀疑你的代码
就是有问题」—— 他是对的。实测对照：

| | 数量 |
|---|---|
| vc_redist 实际装的 | 13 个 DLL |
| 我们包里能补出来的 | **1 个**（numpy 带的 msvcp140） |
| Python embeddable 自带 | 2 个（vcruntime140 / vcruntime140_1） |

PyTorch 用到 `msvcp140_1.dll`（C++17 的一部分符号在那儿），
而 numpy/pandas/shapely 的 wheel 都不带它。所以「软件自己补上，
你不用装 vc_redist」这个承诺**从一开始就兑现不了**。

更糟的是判据。为了不误报，我把「python.exe 旁边也算数」加进检查 ——
而那两个 vcruntime140* 是我们自己随包带的，**哪台机器上都在**。
于是一台从没装过 VC++ 的电脑，状态栏照样显示「C++ 运行库 ✓」。
小蔡在网吧那台抓到：「我很明确，网吧的计算机没有装 vc，为什么会打勾！」

连上前面几次，同一个形状栽了四回：

1. `torch/version.py` 在 → 报「装好了」，而 c10.dll 加载不了
2. `models` 目录在 → 报「模型齐了」，而里面是半截的
3. 数 DLL 清单 → 只查一个 `msvcp140.dll`，缺 `msvcp140_1` 的机器放行
4. 数 DLL + 自己的目录 → 没装 VC 的机器也打勾

**每次的反应都是把判断做得更准，第五次该换思路了：不判断。**

小蔡定的方案（2026-09-02）：「计算机重复安装 vc 会不会有问题」→
「没有问题的话第一步就强制安装 vc」。查证下来重复安装确实无害
（[微软文档](https://learn.microsoft.com/en-us/cpp/windows/troubleshoot-vc-redistributable-installation-issues)
说直接跑最新 vc_redist 可修复运行库、不用先卸载；已有更新版本时返回
`0x666` 自己退出）。

于是 `pipeline/vcredist.py`：首启第一步下载并运行 vc_redist.x64.exe，
装完在安装目录记一个 `vc_done.json`。判据从「系统装没装 VC++」
（猜不准）换成「这个软件在这台机器上装过一次没有」（我们自己说了算）。

⚠️ 这个记号**绝不能进安装包**。开发机上只要跑过一次首启流程，
`dist/PDF2Word/` 下就有它，打包会卷进去 —— 那样每个新用户装上都自带
一个假记号，第一步直接跳过，正是这次要修的 bug 的翻版。
已加进 `build_release` 的排除列表，`check_package` 正向盯着。

## 八、发行版怎么分层

分三层，按变更频率切：

| | 内容 | 大小 | 多久变一次 |
|---|---|---|---|
| Layer 0 | Electron + Python embeddable + node + pandoc + 业务代码 | 0.69 GB | 业务代码天天变，其余不变 |
| Layer 1 | mineru 等 pip 依赖（**不含 torch**） | 0.7 GB | 很少 |
| Layer 2 | GPU 运行库（CUDA 版 PyTorch） | 2.8 GB | 首启按需下，不进安装包 |
| Layer 3 | 模型 | 4.6 GB | 基本不变，软件里点「开始下载」才下 |

Layer 2 是 2026-09-02 从 Layer 1 里拆出来的：CUDA 版 torch 解压后 4.2 GB，
打进安装包会让它逼近 GitHub 单文件 2 GiB 的上限，而且没显卡的人也得
跟着下。`install_deps()` 装完依赖会把 pip 顺带拉进来的那份 torch 卸掉。

**`.venv` 不能打包分发** —— 它的 `Lib/` 下只有 site-packages 没有 stdlib，
`os.__file__` 指向开发机的 Python 安装目录，换台机器第一句 import 就死。
换成官方 Python embeddable（自带 `python312.zip` 那份 stdlib）。
实测四关全过：装 pip、装 pymupdf 并真开了一份 16 页 PDF、装 torch 并真跑了
矩阵乘法、打包后 `os.__file__` 指向发行版自己的目录。

安装包用 7-Zip 的 SFX 做自解压 exe：双击 → 问装哪 → 解压完成。
1.37 GB 压到 287 MB（去掉 torch 之后比 09-01 那版小了 70 MB）。

**更新只推业务代码那 0.5 MB**：安装包里 99.8% 是永不变的东西，
让老师为一个 bug 修复重下 287 MB 是荒谬的。检查更新 → 自动下载 →
校验 SHA256 → 自动解压覆盖 → 提示重启，全程不用打开 GitHub。

⚠️ 更新包里的路径必须跟发行版的实际结构对齐：前端在源码里是 `app/`，
   在发行版里是 `resources/app/`。写错了**不会报错**，只会安静地
   只更新一半（Python 那半路径一致所以是好的），用户还以为更新成功了。

完整规矩见 **`docs/RELEASE.md`**（版本号规则、打包命令、命名规矩、
上传清单、不能破坏的硬约束）。

### 安装包的默认路径：从 v0.0.1 起就没生效过（2026-09-05 查明）

**现象**：安装包的默认路径是**安装包自己所在的目录**。从浏览器下载后
双击，默认就填下载文件夹 —— 而那种目录很多人定期清理，一清就把软件
连同 4.6 GB 模型一起删了。

**根因**：项目用的是 `7z.sfx`，那是 7-Zip 官方的**普通解压模块**，
只认 `Title` / `BeginPrompt` / `Progress` / `RunProgram` / `Directory` /
`ExecuteFile` / `ExecuteParameters`。而 `InstallPath`、`GUIMode`、
`OverwriteMode`、`ExtractPathText`、`ExtractTitle`、`ExtractDialogText`
这六个是第三方修改版 `7zSD.sfx` 的扩展，**官方模块全部静默忽略**。

验证方式：把六个安装包的 SFX 配置段从 exe 二进制里解出来核对，
全都写着 `InstallPath="D:\PDF2Word"`，而实际行为是用 exe 所在目录。

**做法（A 方案，已实施）**：删掉那六个不生效的字段 —— **留着比不写
更糟，它让人以为设过默认路径了** —— 改成在 `BeginPrompt` 里把这件事
直接讲给用户。顺带修了一条写反的注释（原来写着「GUIMode=2 是问用户
解压到哪」，实际含义是**完全隐藏解压对话框**）。

**B 方案（换第三方 sfx 模块）评估结论：不划算。**

| | star | 最后提交 | 最新发布 | LICENSE |
|---|---|---|---|---|
| chrislake/7zsfxmm | 69 | 2020-05 | **2017-06** | LGPL-3.0 |
| cosmomill/7zsfx | 1 | 2017-04 | 无 | **没有 LICENSE** |

后者直接排除（没 LICENSE 等于保留所有权利）。前者九年没发新版，而且
**第三方 sfx 模块会抬高杀软误报率** —— 我们的 exe 本来就没有代码签名，
已经会触发 SmartScreen「未知发布者」，再换第三方模块可能从警告变成
直接拦截。加上打包机要多带一个不可审查的二进制、多一条 LGPL 分发义务，
为了「设个默认路径」不值得。

**C 方案（换 Inno Setup）也否掉**：Inno 的卸载程序只删它装过的文件，
而运行时产生的模型 4.6 GB、日志、appdata、_tmp 全不在记录里，卸载后
原样留着 —— 反而比现在的「直接删文件夹」更脏，正好打在核心承诺上。

### 还没做的

1. **转换报告**：原设计的第 10、11 步——标出哪几处公式可疑、哪几页走了 OCR，
   让用户只核对被标出来的地方。
   09-02 做了一半：转不成的公式会点名「第 N 个（原文）」，那一行右边显示
   「N 个公式没转成」，悬停能看到全文。**还没做的**是「哪几页走了 OCR」，
   以及把这些汇总成一份可导出的报告。
2. **代码签名**。exe 没签名，Windows SmartScreen 会弹「未知发布者」，
   老师要点「更多信息 → 仍要运行」。证书一年几百到几千。
3. ✅ **pip 缓存留在 C 盘 —— 2026-09-05 决定不改**（原文见下，留作台账）。

   小蔡的判断：留着，万一别人用得上。**而实测证明这个判断是对的** ——
   扫那 3.9 GB 缓存扫出 `pyside6_addons` 160 MB、`pyside6_essentials`
   73 MB，那是他自己金石工作台那个 Qt 项目下的；还有 `torch-2.13.0+cpu`
   也是别的项目的。**pip 缓存按 Windows 用户走，不按 Python 环境走** ——
   开发环境的 .venv、发行版的 embeddable Python、别的项目全往同一个
   目录里塞。改 PIP_CACHE_DIR 等于把公共缓存拆成私有的，反而更费流量。

   **代价**：README 里「不留 AppData」那句要跟着改（已改）。
   **补偿**：新版本的环境检测里会**列出这个缓存并按包名给出明细**，
   标清楚哪些是本软件的、哪些是别的程序的，让用户自己决定删不删 ——
   不显示的话，这几个 G 就是用户永远解不开的谜（AppData 是隐藏
   文件夹、文件名是哈希、扩展名还是 .body）。

   以下是当初记的原始分析，留着当台账：

   `torchdep.install_argv()` 既没有 `--no-cache-dir` 也没设
   `PIP_CACHE_DIR`，所以装 GPU 运行库时 pip 把下载的 wheel 缓存到用户的
   `AppData\Local\pip\cache\http-v2`。实测那个目录 **4125 MB / 1452 个
   文件**，最大单文件 2626 MB 正是 torch 的 wheel。

   `pip cache info` 显示 `locally built wheels` 是 **0 个** —— 里面
   100% 是下载副本，**不含任何已安装的东西**。删掉不影响 torch 能不能用
   （已装的包在 `runtime/python/Lib/site-packages/torch/`），唯一后果是
   以后重装要重新下 2.6 GB。

   对照：模型 4.6 GB 落在 `<安装目录>/models/`、torch 本体落在
   `<安装目录>/runtime/python/Lib/site-packages/torch/`，**这两样都是对的**，
   只有 pip 缓存这一处漏了。用户装完后 C 盘白占约 2.6 GB，删软件文件夹
   删不掉，而且他根本不知道它存在 —— 跟第三节那条「运行中产生的一切都
   留在安装文件夹内」和 README 的「不留 AppData」都对不上。

   | | 做法 | 覆盖谁 | 代价 |
   |---|---|---|---|
   | A | 装完 GPU 运行库后自动 `pip cache purge` | 新用户 + 以后还会碰 GPU 运行库的老用户 | 重装要重新下 |
   | B | `PIP_CACHE_DIR` 指进安装目录（**优于 `--no-cache-dir`**） | 只对以后有效 | 无 —— 保留重装免下载的好处，又跟着文件夹一起删 |
   | C | 界面上显示缓存大小 + 清理按钮 | 唯一能覆盖「装完就再不动」那批人 | 成本最高、收益最窄 |

   倾向 **B 打底 + A 补一刀**；只做一件就选 B。

   ⚠️ 改的时候：要加环境变量就加在 `paths.child_env()` **那一处**，
   别散着写 —— 「散着写、漏一处」是这个项目栽过好几次的形状
   （见第三节那张落点表下面的说明）。

    （`--dirty` 可强行）。v0.0.4 正是带着一个未提交的修改发出去的
  · **中文安装路径**（这条原来挂在「还没做的」）→ 09-03 真机炸了：用户装在
    桌面「新建文件夹 (2)」里，MinerU 退出码 1，
    `lid.176.ftz cannot be opened for loading!`。
    **文件就在那儿** —— `fast_langdetect` 先做过 `exists()` 检查；是 fasttext
    的 C++ 层用 `std::ifstream` 按系统 ACP(936) 解那串 UTF-8 字节，对不上。

    🔴 **补丁挂在哪儿，比补丁本身难。这一步在发包前一刻才被抓住。**
    最初是靠 `child_env()` 加 `PYTHONPATH`，让 `site` 自动加载
    `sitecustomize` —— 开发环境完全可行，298 条测试全绿。**但发行版根本
    走不到**：发行版的 Python 是 embeddable 版，目录里有 `python312._pth`，
    而 **`._pth` 一存在，`sys.path` 就完全由它决定，`PYTHONPATH` 被直接
    忽略**。实测发行版子进程的 `sys.path` 只有三条，补丁一次都没生效过，
    而所有测试照样绿着 —— 又一个「开发机上好好的」，形状跟 v0.0.1 那个
    pip launcher 一模一样。

    换过的两个位置和它们各自的死因：

      · 放进发行版 Python 自己的 site-packages 目录 —— 能被自动加载
        （实测可行），但**对老用户无效**：更新包只覆盖 `pipeline/`
        `server/` `app/`，碰不到 `runtime/`
      · 往 `python312._pth` 里加一行 —— 同样在 `runtime/` 下，同样的问题

    最后落在 `sitepatch/run_mineru.py`：一个引导脚本，先 import 补丁再把
    模块名转交给 MinerU 的 CLI。用**脚本路径**启动时 Python 会把脚本所在
    目录放进 `sys.path[0]`，这个机制既不看 `._pth` 也不看 `PYTHONPATH`，
    两个环境完全一致；而它在 `pipeline/` 底下，更新包覆盖得到。
    同时满足「更新包能覆盖」和「不依赖 site 机制」的位置，只有这一个。

    ⚠️ **否掉过一个更漂亮的方案**：Windows 8.3 短路径名。它能一招治所有
    吃 `char*` 的 C++ 库，但 Win10 起非系统盘默认关闭 8.3 名生成，
    `GetShortPathNameW` 会把长路径**原样还给你** —— 不报错、不降级，静默失效。
    小蔡的 D 盘实测就是这样。按那个方案做的话，C 盘用户好好的，D 盘用户照炸，
    现象还一模一样。

    同批实测过的其他原生库：`onnxruntime` / `torch` / `pymupdf` / `pandoc`
    在中文路径下都正常（pandoc 连 exe 带输入输出全放中文路径，rc=0）。
    `cv2.imread` 中文路径会**静默返回 None**，但 MinerU 只在 `__main__`
    示例和调试可视化里用它，正常转换不走 —— 留个记录，别哪天被它咬到。
  · **检查更新是最后一个黑盒** → 09-03 改掉。软件里别的下载都摆命令、
    摆日志、摆测速，只有检查更新是「发一个请求然后干等」。改了三处：

      1. 查版本**从依次试改成并发**。原来名单第一条是直连，用户网络封了
         GitHub 就得先等满 6 秒超时才轮到第二条，五条全试最坏 30 秒。
         并发之后实测 1.2 秒，最坏就是单条超时。

         （09-05 又补了个总时间上限 `API_DETAIL_BUDGET` —— 从发出
         请求那一刻算起，超时没回来的那条标 `pending`「未测」而不是
         「连不上」。中间还错过一版「第一个成功就 break」，把六条明细
         砍成一条，见 `PLAN_NEXT.md` 第十一章末节。）

         🔴 **09-05 当天又改了一次，改的是两个数的大小关系。** 原来
         窗口 3 秒、单条超时 6 秒，于是一条**确定不通**的线路要 6 秒
         才超时，永远赶不上 3 秒的窗口，每次都被补成 pending，界面
         显示「未测」—— 用户看着「未测」不知道该怎么办（小蔡报的）。
         现在 `API_TRY_TIMEOUT = 3.5` < `API_DETAIL_BUDGET = 3.8`：
         每条线路自己先超时出结论，窗口降级成防线程卡死的兜底。
         这三个数（还有前端 4 秒的倒计时）的大小关系由
         `test_update.py` 的 `Test三个时间数的大小关系` 盯着。
      2. 每条线路的成败和耗时**交给界面**（折叠成一行，点开是表）。
         既然每条都跑了，这份明细是白捡的。失败那屏尤其需要它 ——
         「连不上 GitHub」没有任何可操作性，「五条里三条超时、两条 403」
         才能判断是断网还是被墙。
      3. 表格行**本身就是选择器**，不加底栏按钮（620×440 的底栏已经满了，
         而且平时没人需要「选」，只在出事时想知道「为什么」）。
         手动选是给网络环境特殊的人留的后门 —— 最快的未必最稳。

    ⚠️ **「响应快」和「下载快」是两回事**，所以线路表默认显示的是查版本
    时白捡的延迟，真实带宽要点「测下载速度」才测。让每个人每次查更新都
    多等几秒去测一个大多数时候用不上的数字，不划算。

    **发版当天又抓到一个**：下载只试一条线路，挂了就整个失败。更新包
    只有 0.5 MB，走 `probe_mirrors` 的「小包不值当测速」捷径 —— 所有
    `bps=0`，`pick_best` 返回 None，于是永远落到名单第一条；实测连挑
    三次全是 `ghfast.top`。所以那句「再点一次会换个源重试」是假的。
    那天 ghfast 的 SSL 正好挂了，**修好中文路径的这一版，用户反而下不下来**。
    改成按顺序试、挂了换下一条；**唯一不换的是校验没过** —— 内容跟原件
    对不上是安全事件，不能拿「多试几个源」去碰运气。

    ⚠️ 没有改成「下载前自动测速挑最快」，那笔账不划算：0.5 MB 正常下载
    1~2 秒，而测速是 7 条各下 2 秒 —— 测速比下载本身还贵。按序试的代价
    只有「第一条挂了才多一次失败尝试」，第一条通的时候零开销。

    🔴 **这笔账 09-05 被推翻了 —— 当时算漏了一项。**「多一次失败尝试」
    不是零成本：`_fetch_one` 的 `urlopen(timeout=30)` 是**连接超时 30 秒**，
    第一条连不上就干等满半分钟，六条最坏 180 秒，而这半分钟里界面一动
    不动。用户报的原话是「点了更新，半天不出进度条」。
    原来那笔账只把「测速的秒数」记在借方，把「失败尝试的秒数」当成了 0。

    改法（v0.2.2）：点更新时若没手动指定线路，**先并发测一次速再下**。
    测速本身就是并发探测，一两秒就能同时探明哪条通哪条不通，正好把
    「等第一条超时」整个绕开 —— 多花两秒，省掉最坏半分钟。测出来的最快
    那条会真的被用上（填进 `st.updPick`），在此之前测速只重排了显示、
    下载走的还是名单第一条，界面上那句「自动（用最快的）」是空头承诺。
    挑线路那一两秒也不留黑盒：主区显示「正在挑最快的线路…」。

    🔴 **v0.2.4 把这件事收回后端一处。** v0.2.2 的做法是**前端**点更新时
    先打一次 `/api/update/probe`，挑出最快的塞进 `st.updPick` 再发下载请求
    —— 那是为了绕开后端的一个坑：`probe_mirrors` 有「小包不值得测速」的
    捷径（`size < 5 MB` 直接返回 `bps` 全 0），而更新包 0.55 MB 正好落在
    里面，于是 `_download_order` 的测速排序拿到一堆 0，排了个寂寞。

    问题是这么一来「自动挑最快」被拆到了前后端两处：界面上写着「自动
    （用最快的）」，真正让它成立的却是前端那段补丁。删掉补丁，后端会
    **静默**退回按名单顺序试第一条，而那句话还挂着 —— 撞「不承诺不存在
    的行为」，而且没有测试拦得住。

    现在 `_upd_work` 调 `download()` 时**故意不传 size**，让后端自己真测。
    前端只管发请求，按后端给的 `_UPD['step']`（checking / probing /
    running）显示在等什么 —— 确认版本那几秒以前是顶着「正在下载 0%」
    装死的，现在也说实话了。代价：`size` 这个参数从此只服务于捷径判断，
    `tests/test_server.py` 里那条断言改成了「不许传」。

    镜像名单同批调整（2026-09-03 十条候选实测）：moeyy.xyz 两项全挂，
    清出两份名单；ghfast / ghproxy.net 的 API 代理变成 403（09-02 还通），
    只从 API 名单拿掉、保留下载能力；新增 gh-proxy.org / cdn / axisnow
    三个（两项全通）。**API 名单和下载名单本来就是两份，别合并** ——
    `api.github.com` 限速 60 次/小时/IP，镜像代理 API 等于让全世界共用
    它那点配额，所以不少镜像直接 403，而文件下载走 CDN 没这问题。
