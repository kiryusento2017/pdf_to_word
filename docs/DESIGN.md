# PDF 转 Word · 设计

一句话：把 PDF 讲义转成 Word，**文字、公式、表格、图片都是原生对象**，不是截图。

金石工作台（`edu_book_generator`）的专精版——那边是「PDF → 题库 → 重新组卷」，
这边只做「PDF → Word」这一段，不入库、不判题、不组卷。

---

## 一、用户装了之后会做什么

```
【首次启动 · 只出现一次】
1. 双击 `启动.cmd` → 打开
2. 自检：显卡 / 转换引擎 / 公式引擎 / Office，四项一次看完
3. 模型没有 → 并发测速各源 → 显示「预计几分钟」→ 最快的默认选中
   （**只是记下源，不在这一步真下载** —— 见第八节）
4. 就绪

【日常】
5. 拖入 PDF（单文件 / 多文件 / 整个文件夹）
6. 列表显示：文件名、页数、**哪几页没有文字层**
7. 点开始转换
8. 最大号字显示「还要约 X 分 Y 秒」，当前文件和阶段降级成小字
9. 完成 → 打开文件 / 打开文件夹
```

第 8 步为什么是剩余时间而不是百分比：MinerU 的阶段进度是真的，但各阶段耗时
差 100 倍（实测同一次转换：「分析版面」16 秒跑完、两个「识别中」合占 91%、
「处理页面」跑满一整条只要 1 秒）。「分析版面 10/10」看着快好了其实才走 6%。
用户只关心还要多久，而页数 × 实测速率能答这个问题。

原设计还有第 10、11 步（转换报告：标出哪几处公式可疑、哪几页走了 OCR，
用户只核对被标出来的地方）—— **没做**，挪到第八节。

第 6 步只报事实，**不下「好 / 差」的结论**（理由见下一节：初版在这里栽过）。
「第 27、28、30 页没有文字层」是客观的，那几页整页当图识别、出错概率更高，
值得单独看一眼；而「这份不会出错」是我们给不出的承诺，给了就是骗人。

## 二、文字准确度的真相（2026-08-31 实测推翻了初版设计）

初版这一节写着「PDF 有文字层 → 走 txt 模式取文字层 → 正文几乎 100% 不出错」。
**三个说法全错**，实测记录在此，免得后人再推一遍同样的错。

### 错在哪

起因是 MinerU 的产物里有个错字：「9. 己知函数」（应为「已知」）。
当时的推理是：这批 PDF 都带文字层，而配置用的是 `method=ocr`（把文字层扔掉
当图片重新识别），所以错字是 OCR 认错造成的，改走 txt 就能消掉。

**这条推理链一环都不成立**。同一份 PDF 跑三种模式：

| 模式 | 正文字符 | 行内公式 | 「己知」 | 「已知」 | 用时 |
|---|---|---|---|---|---|
| txt | 10187 | **131** | 1 | 13 | 202s |
| auto | 10187 | **131** | 1 | 13 | 178s |
| ocr | 8972 | **213** | 1 | 13 | 238s |

「己知」**三种模式都是 1 处**。直接查原 PDF 的文字层：

```
第 4 页文字层：9. 己知函数 ． （1）若 的解集为 或 ，求的…
文字层里「己知」1 次、「已知」13 次
```

**错字在原 PDF 里就是错的**，是原书排版打错的字，跟 OCR 毫无关系。
「有文字层」是真的，「OCR 是错字来源」是凭空接上去的——两件事都成立不代表
它们之间有因果。

### 实测得出的结论

**默认用 `ocr`**：文字准确度三种模式**一样**（错字都是原书的，谁也消不掉），
但 txt / auto 丢了 82 个公式（38%）——文字层里没有公式，原文那句
「5. 已知不等式 [空] 的解集为」中间就是空的，txt 模式直接放弃，
ocr 把那些图形化的公式识别成了 LaTeX。多花 40 秒换 82 个公式，值。

`auto` 也不能用：它对这份 PDF 的判定结果与 txt **一字不差**（10187 字符、
131 公式），等于走了 txt 路线。

### 所以这个软件能承诺什么

| | 能说的 |
|---|---|
| 正文文字 | **不做准确率承诺**。原书本身可能有错字，OCR 也可能认错，我们分不清也修不了 |
| 公式 | 转成 Word 原生对象（可编辑可搜索），转不了的标出来 |
| 表格 | MinerU 的结构，含合并单元格 |
| 图 | 按原书尺寸还原（MinerU 的 200 DPI） |

界面上**不给「文字版 / 扫描版」这种质量暗示**——那会让人以为标了"文字版"
就不用校对。只报客观事实：几页、哪几页没有文字层（那些页整页当图识别，
出错概率更高，值得单独看一眼）。

## 三、架构

```
Electron 外壳  →  spawn Python  →  FastAPI（本地端口）
   前端纯 JS                          ↓
                        probe / sources / extract / tomath / todocx
```

跟工作台同一套骨架，但**`paths.py` 那套「落点全部关进安装目录」并没有搬过来**。
实际落点：

| | 落在哪 | 关住了吗 |
|---|---|---|
| 临时文件 | `<安装目录>/_tmp/extract`（`server/main.py:160`） | 关住了 |
| Word 产物 | 用户自己选的输出目录 | 用户定的 |
| 模型 4.6 GB | **MinerU 自己的默认缓存目录**（用户目录下） | **没关住** |

模型那条是因为下载动作在 MinerU 手里（我们只传 `MINERU_MODEL_SOURCE` 告诉它
去哪个源拿，落点它自己定）。要真管住得给它设缓存路径的环境变量，**还没做**。

### 模块

| 模块 | 职责 | 能离线单测吗 |
|---|---|---|
| `probe.py` | 判 PDF 有没有文字层、几页、是否加密 | 能，纯读 |
| `sources.py` | 多源并发测速、选源、断点续传 | 能，可 mock 网络 |
| `extract.py` | 调 MinerU，按页吐进度 | 进度解析能（`test_extract.py`），真跑要 GPU |
| `tomath.py` | 公式转换，两条路（见下） | 能，纯函数 |
| `todocx.py` | blocks → .docx | 能，纯函数 |

**只有「真跑 MinerU」这一下需要 GPU，其余全能离线单测**——连 `extract.py` 里
最容易错的那部分（解析 tqdm 进度）也是纯函数，不用 GPU 就能测。这个切法是有出处的：
工作台那边 AI 和 GPU 混在业务逻辑里，全量测试一度从 14 秒变成 142 秒还真花钱。

## 四、公式转换：两条路

```
装了 Office → 读本机 MML2OMML.XSL → OMML
没装 Office → Pandoc（打包在 runtime/）→ OMML
```

### 实测数据（2026-08-31，解不等式那份）

Pandoc 3.11 单独跑的结果：

```
Word 原生公式 m:oMath  213 / 213 = 100%
表格 w:tbl             2（含 rowspan 合并单元格）
表格行 w:tr            12
图片 w:drawing         4 ｜ 内嵌媒体 4
残留 $...$ 源码        0
```

关键参数：**`-f html+tex_math_dollars`**。MinerU 的表格是原始 HTML，
若不让 html reader 认识美元符号包起来的是数学，它会把 `\Delta` 转义成 `\\Delta`、
`^` 转义成 `\^`，LaTeX 当场报废（实测：213 掉到 202，残留 11）。

### 决策台账：为什么保留两条路

Claude 建议**砍掉 XSL 分支只留 Pandoc**，理由是：Pandoc 已经 100%，XSL 不可能更好；
一条路 = 一半的测试面；所有人结果一致，不会出现「你机器上的跟我机器上的不一样」。

**小蔡决定保留两条**（2026-08-31）。故两条都实现、都测。

### 不做的事

微软的 `MML2OMML.XSL` **不打包进安装包**——那是随 Office 分发的版权文件，
提取出来再分发是侵权，范围大小不改变性质。读用户自己机器上那份是合法的，
本项目就是这么做。

Office 路径不写死：要扫 `Office16` / `Office15` / 32 位版 / 非 C 盘安装。

## 五、下载源：照搬工作台 B35

每类源内置多个候选；**点下载时并发对所有源各测 2-3 秒实速**；按预计耗时排序、
最快的默认选中；途中掉速自动切次优源 + 断点续传。

三条硬约束：

- **不存历史成绩**——下载是低频动作，现测成本可忽略，旧成绩反而过时误导
- **不用 ping 判优**——很多 CDN 屏蔽 ICMP，且低延迟 ≠ 高带宽
- 界面显示「预计几分钟」而不是 MB/s，**电脑盲直接点开始即可，不必做选择题**

源清单（工作台 2026-08-22 逐个实测验证，假源已剔除）：

- 模型：ModelScope／HF-Mirror／HuggingFace 官方／本地导入
- 依据：Chromium 走 npmmirror 比 Google 官方快 22 倍，torch 却是官方源更快——
  **没有哪个源是普遍最优的**，写死必然坑一批人

## 七、没有 GPU 的机器怎么办（已定案并实现）

小蔡定的方案（2026-08-31）：首次打开时强制检测，满足就继续，不满足让用户
自己选「退出」还是「硬来」——不猜、不替用户做主。

检测手段：`nvidia-smi --query-gpu=name,memory.total,compute_cap,driver_version`
一条命令拿全（本机返回 `RTX 4060 Laptop, 8188 MiB, 8.9, 572.83`）；没有 N 卡时
用 WMI 兜底查显卡名，好区分「没独显」和「有卡但驱动没装」——这两种给用户的
话术完全不同。判据：compute_cap ≥ 7.5（Turing）且显存 ≥ 6 GB。

**实测结论改变了产品判断**：同一份 10 页讲义，GPU 262 秒 / 纯 CPU 460 秒 ——
**慢 2.0 倍，不是十几倍**。没显卡是能用的，只是得等：10 页约 8 分钟、
30 页约 23 分钟。所以界面话术从「会慢很多」（等于没说）改成了具体分钟数，
让人自己判断划不划算。

## 八、没做的事

排在前面的更要紧。

1. **`pandoc.exe` 没有获取途径**。233 MB，在 `.gitignore` 里（对的，不该进 git），
   但 `tools/setup_env.py` 不下载它，`todocx.py:37` 又写死依赖它。
   从 git clone 出来的机器上，没装 Office 的话公式那条备用路直接断。
   要么让安装器去下，要么 README 写明手动放置（现在是后者）。
2. **「开始下载」按钮什么都不下**。它只把选中的源记下来然后跳到选书页
   （`actions.js:151`）。不自己实现下载器是有意的——跟 MinerU 抢活，两边对
   模型清单的理解一旦不一致就会下出一个跑不起来的半套。但**界面语言骗人**，
   而且第一次转换的「还要多久」会偏小（那 4.6 GB 的下载时间没算进去）。
3. **模型落点没管住**（见第三节的表）。
4. **转换报告**：原设计的第 10、11 步——标出哪几处公式可疑、哪几页走了 OCR，
   让用户只核对被标出来的地方。现在只有「成功/失败 + 失败原因」。
   `convert.py` 返回的汇总里已经有公式数、表格数这些，界面没用上。
5. **打成安装包**。现在是双击 `启动.cmd`。用什么打没讨论过。
